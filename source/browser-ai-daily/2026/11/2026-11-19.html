1. Android AppFunctions 1.0：把 App 功能变成系统可发现、受权限管理的 Agent 操作（11/18 正式稳定）

发生了什么：Google 11 月 18 日正式发布 androidx.appfunctions:appfunctions:1.0.0、appfunctions-compiler:1.0.0 和 appfunctions-testing:1.0.0。应用通过声明结构化函数与 KSP 生成服务/元数据，让授权的系统智能体发现并执行 App 的具体功能。Android 官方将其定位为 Android 应用内、类似 MCP 工具的机制；设备需支持 AppFunctions（Android 16 及更高版本且有对应平台支持）。

新在哪里：相对基于截图、Accessibility 或 UI Automator 的“看屏幕再点按钮”，Agent 可以调用声明式、具备参数约束和返回结构的 App 原生能力。权限由平台控制，跨 App 调用需要受限的 EXECUTE_APP_FUNCTIONS 权限；普通第三方 Agent 并不能因为依赖 Jetpack 1.0 就任意调用其他 App。这次是既有 API 进入 stable，不是 11/18 新发明协议。

证据与成熟度：Android 官方发布记录、代码和权限文档已提供；与 Gemini 的端到端 Connected Apps 集成仍在开发者预览/测试者阶段。技术新颖性：中高（移动端 Agent 原生接口成为稳定开发层）；值得实测：高。建议以 Android 客户端的只读搜索/创建草稿 API 做 PoC，检查权限拒绝、参数校验、真实完成状态和与 UI 自动化的调用成本对比。

原始来源：AndroidX AppFunctions 1.0 发布记录（11/18）；Google 官方机制与授权说明；集成与安全建议。

2. Google Stitch Loop：把代码 Agent 的优化目标连接到真实产品指标（11/18 官方新实验）

发生了什么：Google Labs 11 月 18 日公布 Stitch Loop。它连接 GitHub 源码、日志、用户行为和反馈，通过 180+ 数据集成或自定义 MCP/CLI 导入持续分析可改进项，提出候选方案，在隔离云沙箱修改代码并创建 PR，人工审核合并；随后观察线上指标是否变化，必要时再次产生建议。预置的目标包括安全、延迟和无障碍，安全模块宣称结合 Gemini 4 Carbon 与既有 CodeMender。

新在哪里：不是又一个接单写 PR 的 coding agent，而是将现场观察 → 建议与取舍 → 候选修改 → 人工审查 → 上线指标反馈作为长期产品循环；持久产品上下文还可以通过 Stitch CLI/MCP 供其他 Agent 使用。这与“给定 Issue 后自动修 Bug”不同，触发信号来自真实产品目标。

证据与成熟度：这是 Google 官方新实验公告，11/18 开放全球 Waitlist，符合条件的 Google AI Ultra 用户可获优先访问；没有独立成功率、误报率、改进成本或因果 A/B 证明。人工选择方向和审核 PR 是必要控制点，不能称为无人值守自动生产部署。技术新颖性：中高（现有积木组成目标驱动闭环）；值得深入研究：高、当前可直接实测：受访问权限限制。建议关注每条建议的证据链、实验对照、是否存在指标波动误判和 Learn 资产如何沉淀。

原始来源：Google Labs 11/18 官方发布；官方 Stitch CLI 的实验 Loop 工作区命令。

3. Edge 158：WebTransport 提前接收流配额与会话 draining，加上 WebAudio 增量离线渲染（11/18 更新文档，11/19 计划发布）

发生了什么：微软 Edge 158 Web 平台说明最后更新于 11 月 18 日，标明 11 月 19 日版本发布。WebTransport 开始公布 reliability、supportsReliableOnly，允许通过构造参数提示预计的并发入站流数量，以减少服务端被初始 QUIC stream limit 卡住的风险；transport.draining 可提示应用提前创建新连接，并在旧连接仍可用时迁移流。WebAudio 的 OfflineAudioContext 可分块渲染，避免处理长音频时一次性分配整段输出 Buffer。

新在哪里：这些是对长期连接生命周期、初始流并发及受内存限制的音频计算提供底层 API 支持，适合语音 Agent、实时媒体与端云协同。与此同时，Edge 158 文档列出了声明式 <install> 元素和 navigator.install()，由浏览器接收更明确的 PWA 安装意图；需要用户确认。

证据与成熟度：官方文档明确记录这些能力，但截至本期整理时未独立确认 Edge 158 稳定版已在所有平台实际推送。它们是新版本中的实现/行为能力，不是今日首次提出的协议。技术新颖性：中（重要平台落地而非新计算范式）；值得实验：中高。建议模拟 QUIC 流耗尽、服务端 draining、语音长音频合成峰值内存，检查版本兼容和降级路径。

原始来源：Microsoft Edge 158 官方 Web 平台发布说明（最后更新 11/18）。

端侧 AI

今日更有实质性的变化是端侧智能体操作接口进入稳定发布，而不是新的 WebGPU 模型解码倍数。AppFunctions 提供系统权限和原生 App 动作边界；对有本地大模型的 Android 客户端，可以让模型选择受约束的操作，但执行仍由系统/应用授权检查。今天没有找到能够独立复核、值得头条报道的新端侧推理算法论文。

浏览器 × AI

Web 应用的 WebMCP 提案与 Android AppFunctions 指向相近的架构趋势：应用通过声明自己可执行的操作供受权 Agent 使用，减少靠截图猜测 UI。但二者属于不同平台、不同权限模型，不能直接互操作，也不能暗示 WebMCP 已成为所有浏览器标准正式能力。对 AI Native Browser，应保留结构化工具与 UI 可视化交互两条验证路径。

今天的一个判断

Agent 生态真正发生变化的底层方向，是让应用“明确声明可做什么”，让运行时“明确决定谁能做”，再用可验证的生产结果判断“做得有没有更好”。Android AppFunctions 提供第一、二层的稳定移动接口，Edge 158 给长连接/音频场景补上平台生命周期机制，Stitch Loop 尝试让第三层成为长时间运行的产品改进系统。今天优先建议实测 AppFunctions 授权与真实操作验收；Stitch Loop 等开放真实试用与数据再判断是否值得引入工程链路。
