今天最值得看｜Shifter Quantization、Safari 120Hz 工程实验与 Draft Calibration

1. Shifter Quantization：让低比特权重直接适配硬件整数矩阵运算

发生了什么：11/24 UTC 提交、11/25 公告的 Shifter Quantization 提出一种新的量化表示。传统分组量化的缩放参数随权重组变化，容易切断原生整数矩阵乘加（MMA）的完整点积。SQ 通过附加共享比特、移位和截断重建硬件原生整数宽度操作数；SHI 变体进一步使用 INT4 Kernel。它优化的是数据表示与算子之间的关系，而不只是把模型文件压得更小。

作者实验Prefill 吞吐相对基线
SQ2 / SHI2 对 llama.cpp Q2_K（4096 token）2.71–3.77 倍
SQ4 对 NInfer 分组整数基线1.43–2.47 倍
SQ8 对 vLLM 在线 FP8（batch=1）提高 27.4%

证据与限制：论文全文还给出 WikiText-2 KL 散度与 RTX A6000、3090、4090、5090 跨 GPU 测量。这是作者特定模型与配置的结果，不能解释为手机端或任意模型的加速倍数；未核实独立实现、代码公开或移动 NPU 复现。

技术新颖性：高；值得研究：非常高；直接移动部署成熟度：低。在同一模型、同等权重预算和相同精度约束下比较普通 INT4、SQ、SHI；分开测量 Prefill、Decode、重建成本、内存和能耗，确认目标 GPU/NPU 能否高效执行整数算子。

2. iOS Safari 120Hz：利用合成器滚动与 OffscreenCanvas 获得高频交互

发生了什么：Rida F’kih 于 11/20 发布 可交互工程文章，11/25 进入 Hacker News 热门。作者用浏览器合成器原生滚动承接交互，分析 UI Process 与 Web Process 的滚动位置 IPC；利用空 requestAnimationFrame 循环触发位置刷新，按需激活 ProMotion，再通过 transferControlToOffscreen 取得 OffscreenCanvas，让 Canvas 更新绕过普通页面渲染节奏。作者报告演示获得 120Hz 输入和 Canvas 输出。

技术差异：这不是 Safari 新 API 或关闭 60fps 限制的通用开关，而是组合既有滚动合成器与 OffscreenCanvas 呈现路径。普通 DOM 仍可能受 60Hz 更新限制，设备刷新率、低电量模式与页面可见性也会影响结果。文章包含交互演示；社区讨论不是独立的仪器测量，本期未真机验证。

技术新颖性：中高（工程路径）；值得实测：非常高。在 iPhone ProMotion 与普通 60Hz 设备上分别比较 Safari 和 WKWebView 的 DOM、Canvas、OffscreenCanvas，采集输入采样率、实际呈现帧、掉帧、CPU/GPU、功耗与内存，尤其避免把 JS 回调频率误当成屏幕真实呈现频率。只在必要交互期间启用高刷新，关注非标准组合未来的兼容性。

3. Draft Calibration：不重新训练模型，通过概率校准提升推测解码接受率

发生了什么：UIUC 与 Microsoft 的 研究（11/24 UTC 提交、11/25 公告）发现，部分 Draft Model 虽能预测最可能的 token，却往往给它过低的概率，降低与 Target Model 的分布重叠。对 Draft logits 使用事后温度缩放即可改善接受率；保持目标分布与正确的接受/拒绝采样算法不变。论文也研究更复杂的校准头。

证据：全文附录 B.3在九种模型/并发配置中报告平均每轮接受长度增加 8.82%–10.89%，输出吞吐增加 5.13%–22.08%。属于作者服务端实验，不代表手机端结果或所有单次运行均有收益。

技术新颖性：中高；值得实测：高。温度缩放本身不是新算法，价值是把校准用于 Draft 与 Target 的概率匹配。建议固定采样参数和任务保留集，测试不同 Draft 温度，比较接受长度、TTFT、Decode 吞吐和实际能耗；不能把提高接受率当作模型能力提升。

Browser Self-Improvement

MetaFORGE：执行证据驱动持久 Skill 和跨任务记忆优化。 11/24 UTC 提交的 论文研究 MPI C 并行程序生成，以正确性、编译诊断、静态分析、运行时与负载不均衡构造奖励，使用文本反馈重写 Skill，并从有效结果提炼外部记忆。六个任务、三种负载规模的作者实验中，跨任务保留集使用冻结记忆；另有 zero-update 实验，只使用迁移后的 Skill，不检索、不重写，三个保留任务的运行时间分别降低约 11.8%、18.0%、25.0%，全部通过正确性测试。全文 B.9/B.10说明训练结果每折只产生一次，统计结论受共享训练结果和任务样本约束。

闭环：Observe（测试及运行时测量）→ Diagnose（基于诊断与反馈分析）→ Improve（改写 Skill）→ Verify（编译、正确性及性能评估）→ Learn（提炼记忆并验证迁移）。属于研究环境的 Harness 改进闭环，不是浏览器内核或生产 Canary 的实证。迁移建议：固定浏览器回归集，独立评估规则正确性、内存和性能；训练与保留任务隔离，冻结 Skill 和记忆后再测新站点，分别评估 Skill、记忆检索和迭代的贡献。未核实独立复现或完整开源代码。

今天的一个判断

端侧计算优化的关键是减少实际无效工作，而不仅是降低模型参数位数。 最容易安排的实验是 iOS Safari/WKWebView OffscreenCanvas 的真实帧率和功耗对照；推理方面优先研究 Shifter 的硬件映射，Draft Calibration 可作为低成本验证候选。对自主改进，MetaFORGE 的冻结 Skill 与保留集验证比单看训练奖励更有价值。
