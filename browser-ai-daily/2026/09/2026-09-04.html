浏览器 × 端侧 AI 日报

今天最值得看的不是新模型，而是浏览器正在更明确地成为 Agent Runtime：WebMCP 开始出现“审计 → 实现 → 真浏览器验证”的开发闭环；同时，纯浏览器内 Agent 继续把本地文件、Pyodide、OPFS、WebMCP 和可回滚修改放进同一个运行时。

2026-09-04 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

WebMCPAgent Engineering

WebMCP 开始有“审计 → 实现 → 真浏览器验证”的完整工具链

Era Labs 的开源 webmcp 插件把网站 Agent-ready 改造拆成三个步骤：只读 audit、实现 document.modelContext 工具、再通过 @ora-ai/webmcp-verify 启动真实 Chrome，枚举并执行页面工具。它还带有 fixture、eval cases、bridge package 和安全检查。

为什么值得关注：WebMCP 正从“一个 API 草案”变成可测试的工程工作流。更关键的是 verify 不是读代码判断，而是在真实浏览器里调用工具，开始接近浏览器 Agent 需要的 Runtime Contract Test。

GitHub · Chrome WebMCP

Browser RuntimeLocal-first

EO2Weave：把文件、Python、WebMCP 和 Agent 都塞进浏览器 Runtime

9 月 3 日公开的 EO2Weave 走的是非常“浏览器原生”的路线：File System Access API 访问用户明确授权的目录，SQLite WASM + OPFS 保存状态，Pyodide 在浏览器执行 Python；配套扩展负责发现 WebMCP 工具，并可选接入本机 Native Host。

产品启发：这比“网页里放个聊天框”更接近 AI Native Browser：浏览器本身承担存储、计算、文件权限、工具发现和回滚。它还给每次文件修改保留 diff、快照和回滚，这类机制值得直接迁移到 Browser Agent 的可逆操作层。

GitHub

WebKitVerification

补推 WebKit：Safari 27 为了修 top-level await，重写整个 ES Module Loader

WebKit 9 月 2 日披露，Safari 27 为了彻底解决 top-level await 的执行顺序与未初始化访问问题，把旧的 self-hosted JavaScript module loader 整体替换为原生 C++ 实现，并直接按 ECMAScript 模块算法重建。

Self-Improvement 启发：更值得看的是验证方式：Bun 提供历史失败 case；WebKit 自己生成复杂 module graph 做 differential fuzzing；再跑 test262、WPT，并持续 daily-drive 新实现。这里是非常标准的 Regression → Rewrite → Generated Tests → Cross-engine Differential → WPT → Daily Use 闭环。

WebKit

Chrome DevToolsLocal Workspace

补推 Chrome DevTools：Automatic Workspace 把页面与本地源码映射自动化

Chrome DevTools 新增 Automatic Workspace connection：本地开发服务器通过特殊的 devtools.json 描述工作区后，DevTools 可以自动把网页资源映射到本地源文件，Sources 中的修改直接保存回项目文件。

Browser Agent 启发：这条能力对“浏览器里 Diagnose → 本地代码 Patch”很关键。未来 DevTools Agent 可以直接从当前页面、Trace、Console 定位问题，再通过可验证的 workspace mapping 落到准确源文件，而不是让 Agent 猜文件路径。

浏览器技术

WebKit 的 Module Loader 重写是一份很好的浏览器工程闭环样板

旧实现源自 2016 年已废弃的 WHATWG Loader 思路，后续顶层 await 只能不断补丁。WebKit 最终选择删掉旧 loader，从规范调用图出发逐个实现 C++ 操作。

历史兼容 Bug
   ↓
收集 Bun / WebKit Regression Cases
   ↓
重写核心 Loader
   ↓
Generated Module-Graph Fuzzer
   ↓
与其他 JS Engine 做 byte-for-byte Differential
   ↓
test262 + WPT
   ↓
Daily Drive
   ↓
Merge

这比单纯“AI 生成 Patch”更接近我们真正需要的 Browser Self-Improvement：任何大改都必须携带自动生成的验证证据。

端侧 AI

过去 24 小时没有发现比本周 WebGPU kernels / Hybrid Compute 更强的新端侧底座

今天没有用普通模型发布填数量。更值得关注的端侧变化仍然是 Runtime 层：浏览器内 Python、SQLite WASM、OPFS、本地文件权限与 WebMCP 正被组合成一个可运行 Agent 的本地执行环境。

浏览器 × AI

WebMCP 的下一阶段不是更多 Tool，而是 Tool 的工程质量

目前逐渐形成的真实工作流是：

User Journey
    ↓
Audit
    ↓
Tool Contract
name / schema / permission / reversible boundary
    ↓
Implement document.modelContext
    ↓
Real Browser Verification
registration / invocation / error / cancellation
    ↓
Eval Cases
    ↓
Production Telemetry
判断：网站是否“Agent-ready”最终不会只看有没有 document.modelContext，而会看 Tool 是否可验证、权限是否清楚、失败是否可恢复，以及用户流程是否真的能完成。

Browser Self-Improvement

今天的新关键词：Runtime Contract Testing（运行时契约测试）

过去几天一直在讨论 Independent Verification、Evidence-Carrying Artifact。今天 WebMCP verify 和 WebKit module loader 给出了更具体的一层：不要只验证最终任务成功，要验证 Browser Runtime 每个结构化能力的契约。

Agent / Patch
    ↓
Runtime Contract
    ├─ Tool 是否注册
    ├─ Schema 是否正确
    ├─ Action 是否真的执行
    ├─ Error / Abort 是否符合语义
    ├─ Origin / Permission 是否生效
    └─ 是否可回滚
    ↓
Generated / Historical Cases
    ↓
Independent Browser Run
    ↓
Evidence Bundle
迁移到 Chromium：除了 WPT 和 benchmark，可以为 DevTools MCP、WebMCP、Browser Harness、CDP action、Local Bridge 都定义 contract tests。Agent 每次修改这些能力时，先跑结构化契约测试，再进入性能和端到端 benchmark。

闭环走到哪

WebMCP 工具链：Audit → Patch → Real Browser Verify → Eval，已经覆盖 Improve / Verify，缺生产 Telemetry 和自动 Learn。

WebKit Module Loader：Regression → Rewrite → Fuzz / differential → test262 / WPT → daily drive，覆盖 Observe / Improve / Verify，非常接近浏览器核心工程的高质量闭环，但没有 AI 自动 Diagnose / Patch。

EO2Weave：主要是 Runtime 架构信号；它的 diff / snapshot / rollback 提供了可逆操作能力，可作为未来 Agent 自改进的安全底座。

今天的一个判断

Browser Self-Improvement 的验证层应该从“Benchmark”继续下沉到“Runtime Contract”。

端到端任务成功率太粗。很多失败其实来自 keyboard semantics、frame lifecycle、tool schema、permission、abort、origin、workspace mapping 等底层契约错误。只有这些 contract 先稳定，Agent 上层的规划、学习和自我改进才有意义。

Runtime Contract Tests
        ↓
Component / WPT Tests
        ↓
Benchmark / Trace
        ↓
End-to-End Agent Eval
        ↓
Canary / Telemetry

这会让 Browser Self-Improvement 更像浏览器工程，而不是模型评测。
