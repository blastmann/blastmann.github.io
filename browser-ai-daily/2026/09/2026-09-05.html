浏览器 × 端侧 AI 日报

今天最重要的变化发生在 Browser Agent 的“验证层”：Chrome 官方已经让 Agent 能安装、重载、触发 Chrome Extension，并在真实浏览器里检查结果；Self-Improvement 侧则开始让评测环境本身持续演化，避免 Agent 只会刷固定 benchmark。

2026-09-05 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

Chrome DevToolsAgent Verification

Chrome 官方：AI Agent 现在可以完整管理并验证 Extension 生命周期

Chrome DevTools for agents 在 9 月 4 日新增面向 Extension 的官方工作流。Agent 可以通过 MCP 安装 unpacked extension、列出/重载/卸载扩展、触发 action，并继续读取页面 DOM、截图或检查 service worker 状态。

为什么值得关注：这把浏览器扩展开发从“Agent 写代码，人工去 chrome://extensions 点几下”推进到 Generate → Install → Trigger → Inspect → Verify 的真浏览器闭环。对 Browser Agent 工程来说，这比再增加一个点击工具更重要，因为 Agent 开始能验证自己写出的浏览器能力。

Chrome for Developers · chrome-devtools-mcp

Self-ImprovementBenchmark

Environment Evolution：不只改 Agent，也让训练/验证环境持续变难

9 月 3 日提交的 Environment Evolution 针对长期 Agent 训练提出一个新方向：不是不断从当前模型 rollout 临时生成题，而是把已有环境沿多个维度逐代演化，并按 generation 调度，让任务难度持续跟着 Agent 能力上升。

Browser Self-Improvement 启发：浏览器工程里的 benchmark 也会“老化”。当 Agent 已经熟悉固定 Trace、固定回归模式、固定 WPT case 后，验证集本身必须继续生成更难的跨平台、时序、权限、网络与状态组合，才能持续提供有效学习信号。

arXiv:2609.04128

HarnessDevHarness Evolution

补推 HarnessDev：模型可以自己造 Harness，但“迁移性”仍是硬问题

HarnessDev 把评测对象从任务答案改成 runnable harness：先从最小 seed 创建完整执行系统，再根据下游反馈迭代演化。结果显示，在 coding 与 research 上，模型生成的 Harness 仍明显落后成熟人工 Harness；而且同一 Harness 换执行模型后收益会明显变化。

工程启发：不要假设 Skill / Harness 是模型无关资产。Browser Agent 的 trace parser、tool policy、recovery strategy、context builder 很可能需要标注适配模型与验证环境，并通过兼容性测试后才能复用。

arXiv:2609.01437

Chrome SecurityV8

Chrome 152 修复 V8 在野利用漏洞，继续提醒 Agent 权限边界不能只靠 Prompt

Chrome 9 月 3 日更新 Stable Desktop 到 152.0.7977.82/.83（Windows/macOS）与 .82（Linux）。随后披露的 CVE-2026-85046 是 V8 type confusion，并已存在在野 exploit。

对 Browser Runtime 的启发：Browser Agent 会显著增加网页内容、工具调用和本地能力之间的连接面。任何 Local Bridge、WebMCP、DevTools MCP 都不能因为“Agent 理解了页面”就扩大信任；页面仍是低信任输入，能力隔离必须由 Runtime enforce。

Chrome Releases

浏览器技术

Chrome Extension 开发第一次有了官方的 Agent-native E2E 路径

新的 Extension 工具不只是安装扩展。官方给出的推荐路径已经接近自动验证模板：

Generate Extension
        ↓
install_extension
        ↓
list_extensions / obtain ID
        ↓
trigger_extension_action
        ↓
Inspect page DOM / screenshot
        ↓
Inspect service worker state
        ↓
Modify code
        ↓
reload_extension
        ↓
Re-run verification

这条路径特别适合 Browser Agent / Browser Use 基础设施开发：扩展本身就是 Browser Capability Layer 的重要载体，以前很多失败只在 content script、service worker、权限或 UI surface 真正运行时才暴露，现在这些都能进入 Agent 的验证回路。

端侧 AI

过去 24 小时没有出现比本周 WebGPU Kernel / Hybrid Compute 更值得推送的新端侧底座

今天宁缺毋滥。端侧主线仍然是：小模型负责本地筛选、隐私与路由；高性能部分继续向专用 WebGPU / Metal kernel 和真实设备验证演进。今天的新进展更多发生在 Agent Harness 与验证环境，而不是模型本身。

浏览器 × AI

Browser Agent 的开发闭环开始从网页自动化扩展到浏览器能力本身

之前的 Browser Agent 验证通常是“打开网页 → 点击 → 看结果”。Chrome 这次把被测对象推进到 Extension：

Web Page Automation
        ↓
Extension Lifecycle
        ↓
Service Worker / Content Script
        ↓
Browser Capability
        ↓
Agent verifies its own integration
判断：对 Ghost Browser / Local Browser Bridge 这类项目，未来 E2E 不应该只测一个页面任务，而应该测 Extension 安装、权限、Tab 生命周期、service worker 重启、Native Bridge 断线恢复、action 语义和最终网页状态。

Browser Self-Improvement

今天的新关键词：Evolving Evaluation（演化式验证集）

过去的闭环默认 benchmark 是静态的：

Regression
   ↓
Diagnose
   ↓
Patch
   ↓
Fixed Benchmark
   ↓
Pass → Learn

Environment Evolution 提醒我们，持续改进系统最终会把固定验证集“学透”。更合理的 Browser Self-Improvement 是：

Telemetry / Regression
        ↓
Diagnose / Patch
        ↓
Historical Regression Suite
        +
Generated Hard Cases
        +
Cross-platform Variants
        +
Adversarial Runtime States
        ↓
Independent Verify
        ↓
Canary / Telemetry
        ↓
New Failures feed Environment Evolution
可以怎样迁移：基于真实 Browser regression 自动生成邻近 case，例如把一次 navigation race 扩成不同 frame 层级、缓存状态、网络延迟、BFCache 状态和平台组合；把一次 Extension service worker bug 扩成 sleep/wake、reload、权限变化和断网恢复。这样 Learn 不只是积累修复规则，也会积累更强的测试环境。

HarnessDev 补充了一条约束：Harness 要声明“适配对象”

HarnessDev 的结果显示 Harness 的收益明显依赖执行它的模型，因此 Browser 工程中的长期资产最好带上：

Skill / Harness
├─ Tested model family
├─ Browser / platform scope
├─ Tool / capability version
├─ Eval suite
├─ Last verified date
├─ Expected token / latency cost
└─ Known failure modes

这和前几天的 Evidence-Carrying Artifact 可以直接合并：一份“成功过”的 Skill 不是通用知识，只有在声明范围内被重新验证后才是可信资产。

开源与论文 / 工程实践

ChromeDevTools/chrome-devtools-mcp

官方 MCP 已把 Extension 安装、reload、action trigger、service worker 检查纳入 Agent 工作流。很适合作为 Browser Extension Validation Agent 的直接底座。

GitHub

Environment Evolution

核心价值不是 Terminal-Bench 的具体分数，而是“验证环境也需要持续演化”。这条思路非常适合迁移到 Browser regression / WPT / perf benchmark 自动扩展。

arXiv

HarnessDev

直接评估模型创建和演化 Harness 的能力，并用 hidden downstream tasks 检查是否过拟合。值得作为 Browser Harness 自动演化的 benchmark 设计参考。

arXiv

Modern Web Guidance（补推）

Chrome 把现代 Web 平台、兼容性、性能与安全知识包装为可安装 Agent Skills，并明确建议与 DevTools for agents 组合：真实浏览器诊断后，再按结构化工程知识修改代码。这是 Learn → Skill → Verify 的官方工程化信号。

Chrome for Developers

今天的一个判断

Browser Self-Improvement 的 Learn 不能只让 Agent 变聪明，也要让测试环境跟着变难。

如果一个 Agent 连续修几十次相似回归，固定 benchmark 很快就会失去区分度。真正可持续的闭环应该同时演化三类资产：

Agent / Harness
      +
Engineering Knowledge / Skill
      +
Evaluation Environment / Hard Cases
      ↓
共同进入下一轮

今天 Chrome Extension 的官方 Agent 验证能力正好提供执行表面，而 Environment Evolution 提供生成更难验证任务的方法。两者组合起来，比“让 Agent 自动写更多 Patch”更接近一个可控的 Browser Self-Improvement 系统。
