1. Chrome Mirror Dimension：把“完整可交互互联网”搬进隔离环境做 Agent 安全回归（11/19 官方公开）

发生了什么：Google Chrome AI Security 的 Aaron Selya 与 Charles Qian 11 月 19 日介绍 Mirror Dimension for Agents。它不是在几个静态页面上让 Agent 点按钮，而是构造数千个模拟网站和可持久交互的业务流程，让真实 headless Chrome 在不触及外部互联网的隔离环境中反复执行跨页面动作。其目标是既避免测试时产生真实购买等副作用，又使每次测试都能从完全一致的状态出发。

技术新在哪里：（1）用 gVisor 隔离 Chrome，网络请求经受控代理转到合成站点；Agent 仍看到普通网站域名，减少模型识破“这是测试环境”（eval awareness）导致的行为偏差。（2）在隔离 Chrome 内置入专用受信任根证书，代理为合成站点动态提供 TLS 证书；这是受完全控制的测试网络手段，绝不意味着可在普通用户浏览器里绕过 TLS。（3）由 research、builder、critic 多种开发 Agent 构造功能完整的站点，再通过 Chrome DevTools for Agents 验收表单、ARIA、Console、响应式和交互流程。（4）攻击载荷可落在文字、图像、无障碍标签乃至 WebMCP 返回值，通过后台 X-Sandbox-Injection-Key 选择变体，避免 URL 明显暴露测试身份。

证据与局限：Google 官方披露每位安全工程师每天可以生成并精炼 1000 多个候选攻击测试，称约为单人手工效率 30 倍以上。这是 Google 内部产能数字，不是 Agent 防护成功率；没有公开完整测试集、攻击成功率或第三方复现实测。系统本身也没有公开完整部署代码，不能把设计说明当作可直接安装的 SDK。与此前的可重置 WebArena-Pro 不同，Mirror Dimension 的关键在于让真实域名、真实浏览器行为和动态注入在隔离层统一工作，而非仅增加任务数量。

技术新颖性：高（验证环境、真实协议与对抗样本结合）；值得深入研究：非常高。工程启发：给 Browser Runtime / ERSI 验证台建立 environment snapshot → task → trace → adversarial mutation → independent final-state oracle → regression corpus。先在一两个完全自有的合成站点复刻网络拦截与状态重置，再分别用 Chromium、WebKit、Firefox 比较执行轨迹和隐式测试意识；不应直接复用完整真实网站账户数据。

原始来源：Google Chrome Security 官方技术文章（11/19）；WIRED 11/19 原始采访与补充报道。

2. WebAgents / WebAgentica：Agent 包可以跨托管方传递，但执行权限必须留在用户 Runtime（11/16 论文，7 日补推）

发生了什么：11 月 16 日 23:05 UTC（北京时间 11 月 17 日 07:05）提交的论文 WebAgents: Unbundling Agent Creation, Hosting, and Execution for an Agent-Native Web，提出让作者生成签名 agent.pkg，网站只负责分发，用户自己的 Agent Browser/Runtime 负责校验、授权、模型和工具绑定、预算及执行记录。研究实现已有可查看的 GitHub 源码；仓库 README 当前以 WebAgentica 名称维护，不能将它称为 11/20 新仓库。

技术新在哪里：不是新 MCP 包装。它将发布一个 Agent 的行为描述与授予这个 Agent 实际能力拆开：包仅包含声明式流程、Skills、Schema 和工具要求，不包含可以任意执行的 Python/脚本；包内容以 SHA-256 验证，发行者签名使用 Ed25519。运行时先独立确认签名和信任，再把用户批准的模型、工具、权限与预算冻结成哈希绑定的不可变 Run Plan。在真正执行前再次核对，防止用户审批之后包或工具绑定被悄悄替换。Run Record 单独保留执行结果和审计记录。

证据与局限：论文在自身受控测试中拒绝全部 716 个构造的越权输入，同时允许 295 个配对的正常输入；三类示例包在相同 OpenClaw 解释器中切换本地 Ollama 与 API 模型执行。实验并未证明所有恶意 Agent 都被阻止，也没有证明跨独立实现 Runtime 的通用互操作性。当前开源 README 另记载 Chrome Extension/TypeScript Runtime 与一致性测试，这是仓库后续状态，不能直接回填为原论文已验证的结果。包格式为 agent.pkg 0.1、执行接口为 workflow.v0，均属研究原型。

技术新颖性：中高（可移植 Agent 的权限与发布边界）；值得研究：高，值得直接产品化：暂不建议。建议把“不可变 Run Plan + 执行前二次核验 + 独立 Run Record”加入 Browser Agent Harness 的可验证实验，而不是让分发 Agent Skill 的网站间接拥有用户凭据。还要测试包撤销、发布者密钥轮换、工具重定向、预算耗尽、跨浏览器执行一致性。

原始来源：arXiv 2611.21978 原论文（11/16 UTC）；论文关联原始实现；WebAgentica 研究原型与当前状态。

浏览器 × AI

今天两个方向分别补齐 Browser Agent 的两个基础边界。Mirror Dimension 解决“不伤害真实世界，如何验证 Agent 在真实浏览器里是否安全可靠？”；WebAgentica 解决“第三方发布的 Agent 能否在用户自己的模型、工具与权限下执行，而无需移交权限？”。二者不是已经兼容的产品，但可以组合实验：在签名 Run Plan 授权的情况下，进入隔离虚拟站点执行，再由独立最终状态检查器判定任务完成与权限违规。

Browser Self-Improvement

案例已证实的环节欠缺的部分 / 能否迁移
Chrome Mirror DimensionObserve（真实 Chrome 任务轨迹/页面信号）→ Diagnose（critic/红队检查）→ Improve（合成网站、攻击样本和验证环境迭代）→ Verify（重放测试和攻击测试）Learn 的长期资产格式、Agent 本体/浏览器内核自动补丁与 Canary 没有公开足够证据。可迁移验证理念到 Chromium/WebKit/Firefox；网络沙箱、证书与引擎行为需各自适配。这是评测环境自改进，不是浏览器内核自治改进成功案例。
WebAgents执行前 Verify（包/权限/绑定）及执行 Run Record；部分审计与复测输入没有 Observe→Diagnose→Improve→Learn 的自改进闭环；可作为不同 Browser Runtime 共享的权限/证据协议参考，不应归类为 RSI 论文

可验证的下一步：在相同快照与冻结授权下改变 Agent 的 Skill 或 Browser Runtime 策略，分别重放正常任务和注入任务；一旦误拒绝或未授权动作增加，拒绝推广候选。把失败轨迹、攻击样本、环境版本、最终状态一起存档，才开始形成 Learn，而不是只有一个“测试通过”标签。

今天的一个判断

Browser Agent 的关键新基础设施，正从“能操作网页”向“隔离可重复验证”和“可签名、可授权、可审计的执行契约”演进。最值得优先实验的是 Mirror Dimension 所代表的隔离真实浏览器评测：先证明 Agent 行为能被安全、稳定地重放，再讨论自动优化 Harness 和浏览器内核。WebAgentica 则值得作为执行授权边界参考，避免把网页发布方和用户的执行权限混为一谈。
