浏览器 × 端侧 AI 日报｜2026-09-24

今天最值得看

1. RRSI：Browser Self-Improvement 最大的风险开始从“不会改”转向“改得只会刷 benchmark”

Google Cloud AI Research、UNC、Stanford 等团队提出 RRSI（Regularized Recursive Self-Improvement of Agent Harnesses），专门处理 Harness 自我改进中的过拟合：Agent 在有限任务集上反复修改 prompt、control flow、tools、memory 与 context management，很容易记住 benchmark、接受噪声收益，或靠不断增加复杂度获得表面提升。

RRSI 没有限制哪些 Harness 组件可修改，而是约束“怎么演化”：proposal 侧逐轮缩小一次可打包的修改数量，并保留成功/失败 edit history；selection 侧加入 leakage critic、noise floor、成本约束和结构 pruning。论文在 8 个 benchmark 上报告 evolve split 最高 +14.1 points、5 个 OOD benchmark 最高 +4.7 points，同时相较未正则化演化减少约 30% policy tokens。

为什么值得关注：这几乎直接对应 Browser Self-Improvement 的 Harness 层。一个只在固定 WPT、固定网页集或固定 Pinpoint case 上越调越高的 Browser Agent，不等于真正变强。

工程启发：Browser Harness 的 candidate promotion 应同时检查 benchmark leakage、重复运行噪声、成本增长、跨站点/跨平台迁移，并把 rejected edits 也保存成负证据。

RRSI 论文 · RRSI GitHub

2. WebXPRT 5 首次把浏览器端生成式 AI 做成可重复 benchmark：Z-Image-Turbo + ONNX Runtime Web + Transformers.js + WebGPU

WebXPRT 5 在 9 月 23 日上线实验性的 AI Image Generation workload。它在浏览器内使用 Z-Image-Turbo、ONNX Runtime Web、Transformers.js 和 WebGPU，从文本 prompt 生成图像；一次 warm-up 后连续执行 3 次计分生成，最终报告 images-per-minute。

为什么值得关注：过去浏览器端 AI demo 很多，但真正可以跨设备、浏览器、GPU/driver 重复执行的 benchmark 相对少。WebXPRT 开始把“端侧 GenAI in Browser”拉进传统 Web 性能测试体系。

工程启发：对 Browser × AI 性能回归，可以直接借鉴这种 workload，但不应只保留吞吐分数；建议额外记录 cold/warm、模型下载/加载、adapter/backend、峰值内存、首张图时间、重复运行方差和 correctness。

WebXPRT 5 AI Image Generation 官方介绍

3. Safari Technology Preview 253：WebKit 又推进一轮可直接进入 WPT / Interop 回归的细粒度平台修复

WebKit 9 月 23 日发布 Safari Technology Preview 253，覆盖 WebKit main 320113…321067。首批列出的变化包括 Accessibility 修复，以及 scroll-driven animations 中 style-originated scroll timelines 的跨层级匹配能力。

为什么值得关注：这类 STP release 对 Browser Self-Improvement 的价值不是“又多一个 CSS 特性”，而是它提供了持续变化的真实引擎目标：Agent 的兼容性知识、WPT diagnosis 和自动修复都必须跟着 engine head 持续重验证。

工程启发：可以把 STP / Canary / Nightly 作为 pre-stable verifier，自动跑重点 WPT、站点兼容性与性能 smoke tests；发现 delta 后先 attribution 到具体 engine range，再决定是否进入 bisect / patch。

WebKit：Safari Technology Preview 253

4. Chrome DevTools 近期能力拼起来，已经很接近 Browser Self-Improvement 的 Observe / Diagnose 接口

Chrome 153/154 的 DevTools 月度汇总强调了 DevTools for agents 的细粒度 JavaScript execution controls，同时 Performance 已支持完整 soft navigation、CPU performance tier overrides；AI assistance 也能检查 source 并录制 performance trace。

为什么值得关注：这意味着 Browser Agent 不需要自己重造一套“看懂运行时”的旁路协议。真实 Chrome 的 source、trace、network、runtime permission 可以逐步通过官方诊断表面交给 Agent。

工程启发：Browser Self-Improvement 可以把 Patch Agent 和 Runtime Verifier 分离：前者修改源码，后者只通过真实 DevTools/Trace/benchmark 接口读取证据，减少“自己改、自己判”的污染。

浏览器技术

Safari Technology Preview 253：把 Nightly / Preview channel 当成持续回归输入

STP 253 的变化来自近千个 WebKit main revision 范围。对于自动化 Browser Engineering，与其等 Stable 后再发现兼容性问题，更适合每天/每周对 Preview channel 运行一组固定 WPT + real-site smoke tests，并把新增失败绑定到 revision range。

端侧 AI

WebXPRT 5 开始提供浏览器端 GenAI 的标准化 workload

这次 workload 的意义在于把 WebGPU 推理从项目自己的 microbenchmark 拉到可复现的 Web benchmark。对端侧 AI，更有价值的下一步是把单一 images/minute 拆成加载、编译、首轮、steady-state、内存与稳定性指标，才能定位 Browser / WebGPU / Runtime / Model 各自造成的回归。

Browser Self-Improvement

新增主线：Regularize Improvement Before Promotion

RRSI 给近期主线补上了一个关键 Gate：Self-Improvement 不只要防错误，还要防“只对训练/评测集有效的正确修改”。

迁移到 Chromium 工程：一次 Agent 修改 scheduler、V8 heuristic 或 Browser Harness 后，即使当前 benchmark 提升，也不应该立即写入长期 Skill。至少需要 held-out benchmark / site、另一平台或另一 milestone 做 transfer check；若收益只存在于 evolve set，就应视为过拟合候选。

最值得借鉴的细节：RRSI 后期逐渐把 edit budget 收缩到一次一个修改，使收益更容易 attribution；失败 edit 仍进入 history，成为下一轮避免重复探索的负证据。这和 Browser 工程的小 CL、可 bisect、可回滚原则非常一致。

闭环位置：主要位于 Improve → Verify → Learn 之间，负责决定什么样的 improvement 才有资格成为下一代 Harness / Skill。

开源与论文 / 工程实践

RRSI：建议直接加入 Browser Harness 演化实验

如果做 Browser Harness 自演化，可以直接比较 unregularized evolution 与 RRSI 风格策略：同一组 evolve tasks，另外保留从未参与优化的站点、平台、browser milestone 和任务类型作为 OOD set；同时记录 task success、policy tokens、tool calls、latency 与 Harness complexity。真正值得保留的是能够跨环境迁移的修改，而不是 evolve score 最高的修改。

今天的一个判断

Browser Self-Improvement 下一阶段最需要防的，可能不是 Agent 改坏自己，而是 Agent 很成功地把自己优化成一个只会做固定 benchmark 的系统。

因此“提升”必须同时满足可归因、超出噪声、成本合理、没有 benchmark leakage，并能在 held-out 网站、平台、milestone 或任务类型上迁移。Browser 工程原本就强调小 CL、独立测试、跨平台 regression 与 Canary；RRSI 的价值，是把这些原则正式带进 Harness 自我演化。
