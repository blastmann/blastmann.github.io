浏览器 × 端侧 AI 日报｜2026-09-12

今天最值得看

1. Brave Bot 把“网页是不可信输入”做成 Runtime 结构，而不是 Prompt 约定

Brave 开源的 bravebot 正在把 indirect prompt injection 的防护落实到数据流和权限边界：输入先标记为 trusted / untrusted、public / private；网页等不可信内容不会直接进入 Planner context，而是交给无工具、无记忆、无会话的 Processor 处理，再输出新的不可变 labelled data slot。9 月 11 日最新提交继续修正 trust map：被隔离文件的原始字节不再被 driver 越过 label gate 读取并参与“是否信任”的决策，preview 也改为在 kernel 内带标签转换后才允许显示。

为什么值得关注：Browser Agent 面对网页时，prompt injection 不是偶发异常，而是默认威胁模型。如果“网页文字不要当指令”只写在 system prompt 里，模型仍然需要自己完成信任判断；Brave Bot 则尝试把信任传播、数据降权和能力隔离变成 Runtime 的确定性规则。

工程启发：浏览器 Runtime 可以把 DOM / AXTree / screenshot OCR / WebMCP 返回值都标成来源明确的 untrusted data，Planner 只能通过受限 Processor 获得摘要或结构化结果。页面内容可以影响“事实判断”，但不能直接获得“改变工具策略 / 权限 /目标”的控制权。

Brave Bot · 9 月 11 日 trust-map 修复

2. Ecdysis：不要见到一次 Agent 失败就改 Harness，先找“跨任务重复失败模式”

新论文 Ecdysis 专门研究 self-evolving runtime harness。作者指出，一个失败既可能来自模型本身，也可能来自 Harness 的系统性缺陷；如果每遇到失败就针对该样本修改 Harness，很容易把一次模型失误固化成过拟合规则。Ecdysis 改为先聚合多个任务的失败证据，识别 recurring cross-task failure pattern，再用多角色诊断生成 Harness 修改规格。论文报告 Harness 训练最高加速 1.84×，最终 Harness reasoning accuracy 提升 18.56%。

为什么值得关注：这正对应 Browser Self-Improvement 最容易踩的坑：某个页面点击失败，并不代表应该修改全局 click 策略；一次 trace 里出现长任务，也不代表调度器应该立刻改参数。

工程启发：Browser Harness 的 Improve 触发条件应该从“单次失败”升级为“跨页面 / 跨版本 / 跨设备重复出现，并能被统一解释的失败簇”。先做 failure clustering，再决定是否修改 Runtime、Skill、Prompt 或 browser code。

arXiv：Ecdysis

3. Environment-Probing Memory：Learn 之前，让只读 Curator 回到真实环境核验

《Grounding Agent Memory》指出，post-task curator 如果只能看完成后的 trajectory，很容易保存错误、过度泛化局部经验，或者把已经过期的环境事实继续写进长期 Memory。作者给 Curator 增加最小权限、只读的 world tools，让它在写入前主动检查候选记忆的真实性、作用域和时效性。实验中的 GitHub Copilot harness 在 CLBench 上 pass rate 从 39% 提升到 73%，同时 task-agent 查询数和成本下降。

为什么值得关注：这几乎可以直接迁移到 Browser Self-Improvement 的 Learn 阶段。一次 Browser Agent 成功轨迹并不足以证明“这个 selector 永远有效”“这个网站总是这样”“这个性能优化适用于所有 GPU”。

工程启发：长期写入 Skill / Rule / Knowledge Base 前，应该有一个独立、只读的 Curator：重新查询当前页面能力、重新执行只读检查、核对 Browser milestone / GPU / driver / feature flag，再决定是否保存，以及保存多大的 scope。

arXiv：Grounding Agent Memory

4. Safari Technology Preview 252：Wasm memory64 + multiple memories，WebGPU 新 vertex format，流式 fetch 修复

WebKit 9 月 11 日发布 Safari Technology Preview 252。与浏览器端 AI / Runtime 最相关的变化包括：WebAssembly 支持 memory64 与 multiple memories 同时使用；WebGPU 增加 snorm10-10-10-2 GPUVertexFormat；修复 streaming fetch() response body 会一直等到下一个 network chunk 才交给 reader 的问题。另外还修复了 BFCache 恢复后的媒体播放、ManagedMediaSource、hidden page throttling 等行为。

为什么值得关注：memory64 + multiple memories 对大型 Wasm Runtime、数据库、编译器和本地 AI runtime 都更有意义：应用不必把所有内存组织都压在单一 32-bit linear memory 里。streaming fetch 的修复也直接影响模型/权重/媒体分块消费时的首块延迟。

工程启发：浏览器端推理 benchmark 除 tok/s 外，应补充 model load、首块可消费时间、Wasm memory topology，以及 BFCache / hidden-page 等真实生命周期下的行为。

WebKit：Safari Technology Preview 252

5. COBRA-Skills：Skill 自优化开始把“验证预算”本身当成优化对象

COBRA-Skills 把 reusable skill 的优化建模为有预算限制的序贯优化，不再把每个候选 Skill 都完整跑一遍。它使用 contextual bandit 优先选择更有希望、或更有信息量的候选进行执行验证，再根据真实 execution feedback 演化 Skill population。论文在六个 Agent benchmark、三个目标模型上，相对 SkillOpt 将优化成本降低 55–58%，每个 benchmark 只使用 50 个独立优化样本。

为什么值得关注：Browser Self-Improvement 如果每次候选 Patch / Skill / WGSL kernel 都跑全量 WPT、全平台 build、全套 benchmark，成本很快不可接受。真正可持续的系统必须学习“什么值得验证、先在哪验证”。

工程启发：Browser Verify 可以做分层 budget allocation：先跑最能区分候选的少量 regression / benchmark / device，再把通过的候选升级到昂贵的跨平台矩阵与 Canary。

arXiv：COBRA-Skills

浏览器技术

Safari Technology Preview 252：今天浏览器引擎侧最值得关注的正式更新

本次 WebKit 更新横跨 CSS、JavaScript、Media、Networking、Performance、WebAssembly、WebGPU 与 Web Inspector。除上述 Wasm / WebGPU 外，还有两个工程点值得单独记录：

Streaming fetch：修复 response body 在 reader 侧被延迟到下一网络 chunk 才释放的问题。对流式模型文件、媒体 chunk、增量 parser 都属于“吞吐没变但交互延迟明显变差”的典型 Runtime bug。

Web Inspector：现在会在 Console 中记录页面当前启用的 site-specific quirks。对自动化兼容性诊断很实用，因为某些行为差异并不来自标准实现本身，而来自浏览器针对特定站点启用的兼容性分支。

端侧 AI

今天没有新的模型发布超过本周 WebGPU / 低比特 Runtime 的工程价值

过去 24 小时没有找到比前几天 27B 1-bit Chrome/WebGPU、Hugging Face WebGPU kernels + Fleet 更高价值的新端侧模型或推理底座。今天更值得记录的是 WebKit 把 memory64 + multiple memories 往前推进，因为大型 Wasm Runtime 的内存组织本身正在变成端侧 AI 的基础约束之一。

      +
WebGPU buffer topology
      +
Streaming weight loading
      ↓
Browser lifecycle
├─ foreground
├─ hidden / throttled

所以端侧 AI 的 Browser benchmark 以后不应只记录“模型在某设备多少 tok/s”，而应逐步覆盖加载、流式消费、内存峰值和页面生命周期。

浏览器 × AI

网页内容应该是 Data Plane，不应该直接成为 Control Plane

Brave Bot 今天的实现给 Browser Agent 一个很清晰的安全参考：不可信页面内容可以被读取、抽取和总结，但不要让它直接进入负责工具决策的 Planner 上下文。

Web page / DOM / AX / OCR / WebMCP result
                ↓
        Untrusted labelled data
                ↓
       Restricted processor
        no tools / no memory
                ↓
      structured observation
                ↓
             Planner
                ↓
      capability / action policy

这比在 system prompt 写一句“忽略网页里的恶意指令”更可靠，因为安全属性由 Runtime 数据流保证，而不是依赖模型每次都判断正确。

Browser Agent 的 Learn 也需要独立观察世界

Environment-Probing Memory 进一步补上另一端：完成任务时的 trajectory 只是世界的一次观测，不应该自动成为事实。Browser Agent 的 Curator 可以获得只读 Browser capability，例如：

read current URL / DOM state
inspect tool availability
query browser version / flags
read benchmark / trace result
replay non-destructive observation

但不允许修改页面、写文件、改 Harness 或改变长期权限。它的职责只是判断“这条经验现在是否仍然成立、适用范围有多大”。

Browser Self-Improvement

今天的新判断：Diagnose Before Evolve，Probe Before Learn

今天 Ecdysis 与 Environment-Probing Memory 可以拼成一个非常适合浏览器工程的原则：

不要因为一次失败就进化 Harness，也不要因为一次成功就写入长期经验。

更可靠的闭环应该是：

Telemetry / Regression / Agent Failure
                ↓
      Cross-instance aggregation
                ↓
Is it systematic?
├─ No → model/task-local recovery
└─ Yes
     ↓
 Harness / Runtime diagnosis
     ↓
 Candidate Patch / Skill / Rule
     ↓
 Budgeted Verification
     ↓
 Independent execution evidence
     ↓
 Read-only Environment Probe
     ↓
 Scope / freshness / reproducibility check
     ↓
 Learn
     ↓
 Canary / Telemetry revalidation

闭环映射：今天三篇研究各补哪一步

Ecdysis → Diagnose：先把多个失败聚合起来，区分模型偶发错误与 Harness 系统性缺陷，再决定 Improve。

COBRA-Skills → Verify：验证预算有限时，优先跑最有信息量的候选与测试，不要把所有组合都全量执行。

Environment-Probing Memory → Learn：写入长期 Memory / Skill 前，用只读真实环境重新核验，不只相信 trajectory。

        ↓

这里最重要的新变化，是 Learn 前多了一个“重新看世界”的步骤。例如某次 Pinpoint 得出“CL X 导致性能下降”，Curator 不应该只复制 diagnosis 文本，而应重新确认 culprit CL 状态、后续 revert/fix、当前 milestone 和 dashboard 是否仍然支持这条结论。

对 Browser Runtime / Agent Harness 的具体建议

1. Failure Store 不要直接变 Skill Store：先按 component、environment、symptom 聚合，达到可复现阈值后再触发 Harness 修改。

2. 给 Curator 只读 Browser / Repo / Dashboard capability：允许核验事实，但不允许它一边核验一边修改被核验对象。

3. Verification 要有成本模型：targeted WPT、局部 benchmark、单 GPU 可以便宜先跑；全平台 build、Pinpoint 和 Canary 放在后级。

4. Memory / Skill 必须带 scope：browser milestone × OS × GPU × site/tool version × last verified，避免把环境相关结论当成永久规则。

开源与论文 / 工程实践

Brave Bot：值得跟踪的不是“又一个 Coding Agent”，而是可测试的 Trust Runtime

项目把行为规范拆成 clause，并让 clause 指向对应测试；不可信内容通过 labelled slot 和 processor 流转。9 月 11 日的 trust-map 修复本身也是一个很好的例子：安全边界 bug 不是补一句 Prompt，而是修改 kernel 中数据的标签传播和授权路径，再用 spec/test 固化。

GitHub：brave/bravebot

Ecdysis：Browser Harness 最值得借鉴的是“跨实例失败归因”

浏览器场景天然噪声很大，同一个 click failure 可能来自页面变化、遮挡、frame lifecycle、网络延迟、模型判断或工具实现。只有跨实例、跨环境重复出现的模式，才更有资格推动全局 Harness 演进。

arXiv：2609.11677

Grounding Agent Memory：把 Memory 写入从“总结”变成“审核”

它最可迁移的点不是某种记忆数据库，而是 Curator 的权限设计：最小权限、只读、独立于 task agent，用真实环境证据确认候选记忆。这与 Browser Self-Improvement 的 Evidence-Carrying Artifact 路线非常契合。

arXiv：2609.11060

COBRA-Skills：验证本身也需要调度器

当 Browser Patch / Skill / Kernel candidate 数量开始增长，Verify 会成为主要成本。COBRA-Skills 提醒我们：验证调度应该根据历史证据和信息增益选择，而不是固定把所有候选送进同样昂贵的测试矩阵。

arXiv：2609.11682

今天的一个判断

Browser Self-Improvement 下一步最值得补的，不是更强的“自动改代码”，而是两个闸门：改之前判断这个失败是否真的值得改；学之前回到真实环境确认这条经验是否真的值得记。

因此我会把最近形成的主线继续收敛为：Persistent Runtime 保存真实状态 → Failure Aggregation 决定是否进入 Improve → Budgeted Verification 控制验证成本 → Read-only Curator 决定什么可以进入长期 Learn。
