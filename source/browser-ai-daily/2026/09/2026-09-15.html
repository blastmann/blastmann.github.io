今天最值得看

1. BetterWright：Browser Runtime 开始把持久会话、网络策略、凭证与证据放到同一层

本周值得补推的开源项目 BetterWright，把 persistent Playwright browser、network policy、encrypted credential vault、proof screenshots 和 human handoff 放进一个独立 Browser Runtime。Agent 可以通过 CLI、MCP 或 JS/TS SDK 使用它，而 Runtime 本身不依赖模型。

为什么值得关注：这与最近 BrowserSkill 的 persistent daemon 路线形成呼应：Browser session、登录态、权限和证据不应该跟随短生命周期 Agent 一起销毁。更关键的是，它开始把“允许访问哪些网络”“谁可以填入凭证”“操作后留下什么证明”都变成 Runtime 责任。

工程启发：Browser Self-Improvement 的验证层可以借鉴这种分工：Agent 负责提出动作或改动，Runtime 负责策略约束、凭证注入、截图/状态证据与人工接管。这样换模型、换 Harness 时，安全和证据边界不必重做。

2. GitHub Agentic Workflows 为什么把内置 Playwright 从 MCP 改成 CLI-only：工具面越大，Harness 成本越高

GitHub Agentic Workflows 在 9 月初解释了一个很有工程价值的取舍：内置 tools.playwright 不再默认走完整 Playwright MCP，而只保留 CLI 模式。原因之一是 MCP 会把大量 browser tool schema 注入模型上下文，即使很多工具本轮根本不会使用；需要完整 MCP 的工作流仍可以显式配置。

为什么值得关注：这给 Browser Agent 的 tool design 一个非常具体的反例：把 click、snapshot、trace、evaluate、network 等所有能力都长期注册，并不等于更强，反而可能增加 token、规划和工具选择负担。

工程启发：更合理的 Browser Harness 可以是少量稳定 CLI primitive + 按需发现 capability；只有进入性能诊断、heap snapshot、extension debugging 等场景时，再加载专门工具包。

GitHub：Why the Built-In Playwright Tool Is Now CLI-Only

3. Chrome DevTools MCP 1.9 的方向值得继续追：从“自动化工具箱”转成按能力拆分的诊断面

Chrome DevTools MCP 1.9 已把 JavaScript execution、navigation/initScripts、filesystem roots、source maps 等能力进一步拆分，并继续强化 network、cookie、performance trace 等诊断能力。过去 24 小时没有新的正式版本，但这条路线仍是 Browser Self-Improvement 最值得迁移的基础设施之一。

工程启发：Observe / Diagnose / Verify 可以分别申请不同 capability，而不是让改代码的 Agent 默认拥有所有 Browser 权限。对于自动性能回归诊断，可只开放 trace/network/console；真正需要复现交互时再临时增加 navigation/action 权限。

Browser Runtime 与 Agent Harness 正在逐渐解耦

BetterWright、BrowserSkill，以及 GitHub Agentic Workflows 的 CLI 取舍指向同一个方向：Browser Runtime 应保存会话、策略和证据；Agent Harness 只按任务获得足够小的动作表面。

Persistent Browser Runtime
├─ session / profile
├─ network policy
├─ credentials
├─ trace / screenshot / state evidence
└─ human handoff
        ↑
   narrow interface
        ↓
Ephemeral Agent Harness
├─ reasoning
├─ candidate action
└─ candidate patch / workflow

今天的新判断：Capability Budget（能力预算）

前几期一直在讨论 Capability 是否应绑定 Context。今天再补一个维度：Agent 不只需要权限边界，还需要能力预算。

Observe
  ↓
Diagnose task type
  ↓
Select minimum capability set
├─ trace only
├─ network + console
├─ DOM / AX
├─ browser action
├─ JS execution
└─ filesystem / credential
  ↓
Execute
  ↓
Post-condition evidence
  ↓
Release temporary capability
  ↓
Learn

原因很简单：工具越多，不只是安全面越大，模型需要理解和选择的 action space 也越大。GitHub 把内置 Playwright 改为 CLI-only，就是一个真实工程信号：完整 MCP 能力应该在需要时显式加载，而不是默认常驻。

迁移到 Chromium 工程后，可以把 Self-Improvement Agent 拆成窄角色：Trace Agent 只读 trace/perf dashboard；Culprit Agent 只读源码历史与 bisect 结果；Patch Agent 获得工作树写权限；Verifier 只拿 build/benchmark 与真实 Chrome。这样不仅减少误操作，也更容易判断一次失败究竟来自模型、工具还是权限配置。

开源与论文 / 工程实践

BetterWright：策略与证据进入 Browser Runtime

它最值得借鉴的不是又一个 Playwright wrapper，而是把 network controls、trusted credential filling、proof screenshots 和 persistent browser 放在模型之外。对于 Browser Self-Improvement，这意味着验证证据可以由独立 Runtime 产生，而不是由被测 Agent 自述。

GitHub Agentic Workflows：默认工具面应该尽量小

CLI-only 的选择说明成熟 Harness 会主动控制 tool schema 和上下文成本。Browser Agent 可以把复杂 capability 做成按需 skill/plugin，而不是把所有工具一次性暴露给模型。

今天的一个判断

Browser Agent 下一阶段不应该继续比赛“谁注册的 Tool 更多”，而应该开始衡量：完成同一个任务，最少需要开放多少 Browser capability。

对 Browser Self-Improvement，这会形成一个很实用的工程目标：同样的 Diagnose / Patch / Verify 成功率下，持续减少长期权限、工具 schema、上下文和可变状态。能力更少但证据更强，通常比能力更多但边界模糊更容易形成稳定闭环。
