今天最值得看

1. Chrome 155：chrome.debugger 权限在浏览器接入点生效

发生了什么：Chrome 155 的平台说明确认，受管理设备上的扩展在调用 chrome.debugger.attach() 时，可能因主机访问策略或截图/DLP 策略被拒绝。浏览器返回明确的拒绝原因，而非依赖 Agent 自行遵守提示词。

为什么值得关注：真实用户 Profile 上运行的 Browser Agent 越来越依赖 CDP；浏览器本身才应掌握 Session、截图与主机访问权限。

工程启发：将策略拒绝与普通工具错误分开处理；对授权变化进行回归测试，不能把权限拒绝当作自动重试条件。

Chrome 155 官方发布说明

2. WebGPU 155–156：fragment_depth、压缩纹理和线性色域

发生了什么（10 月 7 日）：Chrome 官方公布 WGSL fragment_depth、texture-compression-unaligned、srgb-linear/display-p3-linear、snorm10-10-10-2，以及 Linux 较新 NVIDIA 驱动上的 shader-f16 支持。不同能力需要分别探测是否可用。

为什么值得关注：新特性涉及 early-Z、纹理边界、HDR 色彩以及端侧 GPU 计算环境。对小模型来说，shader-f16 值得实测，但不能仅凭支持就宣称推理变快。

工程启发：建立 GPU adapter/driver/backend 能力矩阵，验证 shader 输出、颜色、device-lost、显存与实际 tokens/s。

Chrome 官方 WebGPU 更新

3. Chrome 155 WebTransport：Datagram 优先级和流统计增强

发生了什么（10 月 6 日版本）：datagramsReadableType: "bytes" 支持 BYOB 读取；WebTransportDatagramDuplexStream.createWritable() 与 sendGroup/sendOrder 表达 Datagram 发送顺序；WebTransportReceiveStream.getStats() 分开记录网络收到与应用已读取的字节数。

为什么值得关注：对实时媒体和端云协同推理，网络到达、应用消费和发送排队是三种不同的延迟来源。优先级仅代表浏览器已定义的队列行为，不等于端到端网络保证。

工程启发：弱网验证应覆盖 loss、queue、backpressure、P95 延迟和多浏览器兼容，而不是只看连接是否成功。

Chrome 155 WebTransport 发布说明

4. HarnessSecurity-Bench：权限安全与正常任务完成率必须一起测（补推）

发生了什么：10 月 6 日论文分析六种 Coding Agent Harness，包含 23 个任务、五类攻击面、约 2,500 次试验。其受控实验中，开启自动批准后，攻击成功率由 29.2% 上升至 95.6%。这些数据属于特定模型和测试集，不能直接外推到所有 Browser Agent。

为什么值得关注：仅禁止某个工具并不代表敏感操作无法从其他工具路径触达；安全限制也可能妨碍合法任务。

工程启发：同时衡量正常任务完成率、风险操作是否发生、工具开销，并使用独立的安全判定程序。

HarnessSecurity-Bench 论文

5. Chrome 155 JPEG XL：Rust 解码器进入 Blink（补推）

发生了什么：Chrome 155 正式说明加入 image/jxl 解码，使用纯 Rust 的 jxl-rs，支持渐进解码、HDR、宽色域、高位深与动画。

为什么值得关注：新图片格式不仅是压缩率问题，还会影响渐进显示、解码成本和安全面。内存安全的解析器设计尤其值得浏览器工程参考。

工程启发：对新格式建立 fuzz corpus、视觉正确性、P95 解码耗时、内存峰值与旧版本回退验证。

Chrome 155 发布说明 · jxl-rs 源码

端侧 AI

今天未找到足够重要的新端侧模型发布。更值得验证的是 WebGPU 新能力在真实设备上的收益：adapter feature detection、f16 kernel、OOM/device-lost、模型首 token 延迟、吞吐和耗电。API 支持与端侧推理性能是两件事。

浏览器 × AI

Browser Agent 应把 Browser Runtime 作为真实 Profile 的权限与证据所有者：Agent 请求操作，Runtime 负责授权和执行，独立 Verifier 检查结果。对于拒绝、暂不支持、临时错误，需要明确区分，避免错误恢复策略。

Agent 请求 → Runtime Capability Gate
    ├─ 允许 → 执行 → 独立验证
    ├─ 拒绝 → 停止 / 人工授权
    └─ 不支持 → 选择符合相同策略的替代方案

Browser Self-Improvement

今天新增：Alternative-Path Security Replay + Utility-Aware Promotion

业界做到哪：Chrome 155 已有浏览器侧的 attach-time 权限约束；HarnessSecurity-Bench 提供了分别测量合法任务成功和风险行为的实验方法。它们尚未构成“自动修复 Chromium”的完整闭环，但可以直接成为 Verify 的输入。

迁移到浏览器工程：针对同一受保护的敏感操作，验证不同工具调用方式都符合 Runtime 策略；同时确保正常网页和授权自动化没有明显退化。

对 Agent Harness 的启发：版本化保存 policy、allowed/denied outcomes、utility、security oracle 与原始证据；被优化的 Agent 不能同时自行改写验证标准。

闭环位置：重点补强 Build/Benchmark → Verify → Promote；尚无证据表明这两项工作已完成 Chromium Patch → Canary → Learn 的端到端自动闭环。

今天的一个判断

Browser Self-Improvement 的安全验证不能只检查一条工具路径，还应检查同一敏感操作的其他可达路径，并同时衡量合法任务是否受损。

这会让安全验证从“工具列表检查”变成“操作目标 + 权限策略 + 可执行反例”的工程资产，能随浏览器和 Harness 一起回归。
