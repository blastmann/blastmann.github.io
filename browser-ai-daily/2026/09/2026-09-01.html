浏览器 × 端侧 AI 日报

今天没有高价值的新 WebGPU / WASM 引擎发布或端侧模型发布；更值得看的是 Browser Agent 正在收敛出一套更现实的客户端形态：真实 Chrome、本地 Bridge、压缩后的页面语义、明确的人类确认边界，以及可持续监控与调度。

2026-09-01 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

Chrome ExtensionsManifest V3

Chrome Web Store 正式移除剩余 Manifest V2 扩展

Chrome 官方时间线确认：2026 年 8 月 31 日，Chrome Web Store 移除所有剩余 Manifest V2 扩展。Chrome 138 已在 2025 年 7 月全面禁用 MV2；这次变化主要切断旧扩展的商店分发、更新和重新安装渠道，而不是今天才让 MV2 停止运行。

为什么值得关注：对 Browser Agent 很现实。越来越多 Agent 依赖 Chrome Extension 作为客户端能力层，MV3 的 service worker 生命周期、remote code 禁止、权限与网络能力限制，不再是迁移问题，而是 Agent Runtime 必须长期适配的基础约束。

Local Browser AgentMCP

Runbook AI 1.47：真实登录态 Chrome + 本地 Agent + MCP，加入监控与调度

Runbook AI 的 Chrome 扩展在 8 月 31 日更新到 1.47。它运行在浏览器 side panel 中，使用当前真实 Chrome Session，可执行多 Tab 任务、DOM 变化监控和定时任务，并通过本地 MCP Bridge 被 Claude Code、Gemini CLI 等外部 Agent 调用。项目强调页面内容先压缩成简化 HTML，避免每一步把完整 DOM 塞进模型上下文。

浏览器 × AI 启发：这已经非常接近“浏览器内 Observation + 本地 Agent Runtime + 外部 Coding Agent”的组合。尤其值得关注 DOM-diff 先做廉价 Observe、只有页面变化才唤醒 Agent 的设计。

Capability BoundaryHuman-in-the-loop

ChromeBoost 1.1：把“哪些动作必须由用户确认”写进 Browser Agent 边界

ChromeBoost 也在 8 月 31 日更新。它采用 Chrome Extension + localhost MCP server，点击前做 hit-test，输入通过 CDP 发送真实事件；更重要的是，它明确把发布、支付、密码和二次验证码留给用户确认，Agent 完成周边步骤后交还控制权。

为什么值得关注：这比泛化的“Agent 能不能点击”更接近 Browser Capability Layer。浏览器应该对高风险动作建立操作级能力边界，而不是给 Agent 一个长期、全站、全动作权限。

浏览器技术

MV3 已经从“迁移目标”变成 Browser Agent 的固定运行环境

Manifest V2 的最后商店清理意味着，面向 Chrome 的本地 Browser Agent 基本都必须把 MV3 当作不可绕过的平台约束。对 Agent Extension 来说，最值得重新检查的是 service worker 的短生命周期、host permissions、content script isolated world、Native Messaging / localhost Bridge，以及不允许远程加载可执行代码。

工程判断：未来 Browser Agent 的可进化能力不应依赖“动态下载一段新 JS 到扩展里执行”，而应把可变部分放在声明式 Skill、受限 Action Schema、本地 companion process 或浏览器提供的标准 Tool API 中。

端侧 AI

今天值得跟踪的是“Local-first Agent”，不是新的小模型参数

Runbook AI 支持用户自行配置 OpenAI、Anthropic、Gemini、OpenAI-compatible endpoint，也支持本地 Ollama。对浏览器端侧 AI 来说，这种结构比“强制所有任务跑本地模型”更实际：页面观察、DOM diff、权限判断、简单分类可以本地完成；复杂规划再按成本、隐私和设备能力路由到本地或云模型。

变化点：竞争焦点开始从“连接真实 Chrome”向上移动：谁能提供更小的 Observation、更可靠的动作语义、更细的权限、更好的恢复，以及更低成本的持续 Observe。

Browser Self-Improvement

今天最值得迁移的不是自动 Patch，而是 Observe 成本控制与 Capability Policy

Runbook AI 的页面监控采用廉价 DOM-diff polling，只有内容真正变化才触发 Agent。这可以直接迁移到 Browser Self-Improvement 的 Observe 层：不要让大模型持续读完整 Trace、Perf Dashboard 或所有 Telemetry，而先由确定性/轻量规则检测“值得诊断的变化”。

Telemetry / WPT / Perf Dashboard
          ↓

          ↓
Meaningful Change?
  ├─ No  → Stop
  └─ Yes → Agent Diagnose
          ↓
Pinpoint / Trace / Culprit CL
          ↓
Patch / Benchmark / Verify
闭环位置：Runbook AI 主要补强 Observe → Trigger；ChromeBoost 的确认边界对应 Improve/Act 前的 Capability Gate。两者还没有走到自动 Patch → Build/Benchmark → Canary → Learn，但它们给浏览器工程 Agent 提供了两个非常可迁移的 Runtime 机制。

把风险等级变成 Browser Engineering Agent 的一等输入

ChromeBoost 把支付、密码、2FA 等动作硬性留给用户。迁移到 Chromium 工程 Agent，可以按风险区分操作权限：

Low Risk
- collect trace
- query dashboard
- run benchmark
- generate hypothesis

Medium Risk
- generate patch
- local build
- local test

High Risk
- upload CL
- modify security-sensitive code
- change rollout config
- canary / production action
          ↓
Require explicit review / approval

这比简单的“Human-in-the-loop”更具体：审批应该绑定具体 Operation，而不是绑定整个 Agent Session。

今天的一个判断

过去一周连续出现的项目已经足以说明：“Real Browser + Local Bridge”正在成为 Client-side Browser Agent 的一个稳定架构类别。接下来真正拉开差距的不会是“能不能点网页”，而是四件事：

1. Observe 得够小：DOM diff / structured state / event-driven
2. Action 得够真：real input / state-aware / recoverable
3. Permission 得够细：Tab / Origin / Operation / confirmation
4. Learn 得够安全：evidence / provenance / validation / expiry

对应 Browser Self-Improvement，今天新增的工程原则可以概括成 Trigger Before Reasoning：先用便宜、确定性的机制判断是否真的发生了值得分析的变化，再唤醒昂贵的 Agent。对持续运行的浏览器工程闭环，这会直接决定成本和噪声能不能控制住。
