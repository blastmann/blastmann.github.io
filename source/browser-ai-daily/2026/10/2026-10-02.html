今天最值得看

1. Chrome 154 安全更新：FileSystem、Compositing、V8、WebRTC 同时进入修复范围

Chrome Stable 更新到 154.0.8037.97/.98（Windows/Mac）和 154.0.8037.97（Linux），Chrome 154 Android 随后发布并携带对应安全修复。新披露的问题覆盖 FileSystem 授权、Compositing、V8、WebRTC 等多个运行时边界。

为什么值得关注：这些问题横跨权限、渲染、JS 引擎和实时媒体，说明 Browser Runtime 的安全验证不能只围绕单一组件。对于会自动改 Chromium/V8/Compositor/媒体栈的 Agent，安全 regression 必须和性能 benchmark 同级。

工程启发：Self-Improvement 的 Verify 阶段应根据改动依赖图自动选择历史安全 regression、跨源隔离、permission、fuzz regression 与 process-boundary 测试，而不是只跑目标性能用例。

Chrome Releases

2. agent-browser：紧凑 Observation + Runtime Policy 正成为通用 Browser Agent CLI 的基础能力

vercel-labs/agent-browser 近期继续高频更新。项目用紧凑页面 snapshot 和稳定 element reference 避免把完整 HTML 塞进模型，同时提供 session/auth state、network controls、profiling、page comparison、视频与 screenshot 等工程能力；安全侧还有本地 credential vault、domain restriction、destructive-action policy 和用于区分网页内容与工具输出的 boundary marker。

为什么值得关注：它把 Browser Agent 的关键边界拆得很清楚：Observation 应紧凑，Credential 不应进入 LLM Context，危险 Action 应由 Runtime Policy 决定，调试和验证则依赖独立 Evidence。

工程启发：Chromium-native Agent 可以采用相同分层：Browser Runtime 持有 session、credential、policy 与 evidence；模型只接收完成当前决策所需的最小 observation。

agent-browser GitHub

3. WebBrain：把真实已登录浏览器会话桥接给本地 Coding Agent

WebBrain 是近期值得补推的 Chrome/Firefox 开源扩展：它把当前真实浏览器会话通过本地桥接暴露给 Claude Code、Cursor、Codex 等 Coding Agent，也支持 Ollama、llama.cpp 等本地模型。Agent 可以在保留真实登录态的情况下检查 DOM、提交表单并验证 Web 应用。

为什么值得关注：它把“代码 Agent → 真实浏览器 → 验证”这条链进一步产品化，同时再次强调 Browser Runtime 才应该拥有 authenticated session。

工程启发：开发态 Browser Agent 最有价值的不是替代 Playwright，而是成为真实 Runtime Evidence 的桥：代码修改后直接用真实页面状态验证，同时把 credential 隔离在浏览器侧。

WebBrain GitHub

4. Chrome 154 Android：桌面修复同步进入移动 Browser Runtime

Chrome 154（154.0.8037.126）已发布到 Android，官方说明包含稳定性与性能改进，并携带对应桌面版本的安全修复。

为什么值得关注：桌面验证通过并不意味着改进可以直接 Promote。浏览器的同一组件会跨 Windows、macOS、Linux、Android 进入不同 process、driver、permission 与 lifecycle 环境。

工程启发：Promotion Gate 应明确包含 platform rollout：Desktop held-out → Android/mobile replay → Canary telemetry，而不是把 Chrome 当成单一运行环境。

浏览器技术

Browser Runtime 是一组相互连接的信任边界

今天 Chrome 的修复同时触及 FileSystem authorization、Compositing、V8 与 WebRTC。对浏览器工程而言，这些组件不是独立测试岛。性能或功能改动的 verifier 因此需要同时理解 dependency graph 和 privilege boundary。

端侧 AI

端侧模型最适合接收最小可信 Observation

agent-browser 和 WebBrain 都在强化一个实用方向：模型不必拥有 credential、完整 DOM、所有历史和浏览器内部状态。Browser Runtime 可以先做 snapshot、reference、policy 与 credential isolation，再把低风险决策交给本地小模型；复杂规划按需升级到云模型。

业界信号：Chrome 154 同一批修复跨 FileSystem、Compositing、V8、WebRTC，说明真实浏览器风险天然跨组件。Browser Agent 工程则开始把 credential vault、domain restriction、destructive-action policy 等能力放回 Runtime。

迁移方式：每次成功修复的安全问题都应沉淀为可重放 counterexample，并挂到对应 component / dependency / privilege edge。以后 Agent 修改相关路径时，由 dependency graph 自动选择最小安全 regression set。

开源与论文 / 工程实践

把安全修复也变成 Self-Improvement 的长期资产

过去我们更多把成功/失败性能实验沉淀成 Skill、Rule、Test。今天更值得强调的是：安全修复同样应该进入 Learn，但沉淀形式最好不是自然语言规则，而是 executable counterexample。这样未来无论 Patch 是人写还是 Agent 生成，都可以用同一份历史条件重新验证。

今天的一个判断

Browser Self-Improvement 的 Promotion Gate 不能只有“功能正确 + 性能变好”；只要 Agent 能修改 Browser Runtime，历史安全反例就必须成为一等验证资产。

最理想的 Learn 不是记住“这里曾经有一个安全问题”，而是保存能重现问题类别的最小环境、输入、权限条件和预期安全属性，并绑定到 dependency graph。
