浏览器 × 端侧 AI 日报｜2026-09-16

今天最值得看

1. Chrome 把广告 CPU / Network / Density 变成 CrUX 真实用户遥测：Observe 层出现可公开比较的新信号

Chrome 9 月 15 日向 Chrome User Experience Report（CrUX）加入实验性的广告体验指标：Ad Count、Ad Density、Ad Weight (Network) 与 Ad Weight (CPU)。数据来自真实用户，按 28 天滚动窗口聚合；CPU Weight 统计广告 frame 的 JavaScript CPU 时间，Network Weight 统计广告资源的压缩传输字节。

为什么值得关注：这不只是广告产品指标。它展示了 Chrome 如何把浏览器内部的 frame/resource 分类、CPU attribution、network attribution 与真实用户环境结合成可长期观测的 field telemetry。对于 Browser Self-Improvement，真正困难的 Observe 层往往正是“某个子系统到底消耗了多少真实用户资源”。

工程启发：浏览器内部的 AI 优化也应尽量建立类似 attribution：把 CPU、network、memory、GPU、long task、crash 明确归因到 feature / frame / extension / agent action / model session，而不是只看全局页面指标。这样 Agent 才能从 Regression 继续走向可解释的 Diagnose。

Chrome：New ad metrics in CrUX · Measurement methodology

2. Chrome 同时公开广告识别机制：Telemetry 的前提是 Attribution Ground Truth

Chrome 新文档解释了 ad detection 如何结合 network-level filtering 与 script execution analysis 识别广告相关 frame/resource，这些分类既用于 CrUX 指标，也用于浏览器层面对高 CPU / 高网络广告的干预。

为什么值得关注：Browser Self-Improvement 不能只有“指标变差了”，还必须知道是谁造成的。错误 attribution 会让后面的 culprit、patch、learning 全部偏离。

工程启发：可以把同样原则迁移到浏览器 AI：Trace / Perf Dashboard 不只输出 P95，而应附带 component/action attribution 和置信度；自动 Patch 前先验证 attribution 是否稳定。

Chrome：Ad detection in Chrome

3. WebPilot：Local-first Agentic Browser 把运行记录、Browser Profile 与模型选择放在本地 Runtime

近期出现的开源 WebPilot 使用 Electron + Playwright MCP，支持 Ollama、本地/云模型、installed browser channel、已有 Chrome CDP 连接和多种 profile 策略。它会在本地保存 run logs、step traces、artifacts、timing 与最终结果，并提供 browser smoke test；Browser tool schema 还通过版本化的 normalized declaration 与具体模型 provider 解耦。

为什么值得关注：它本身还不是成熟 Browser Self-Improvement 系统，但其 Runtime 分层与昨天的 Persistent Runtime / Capability Budget 主线一致：Browser/Profile/Trace 属于稳定执行层，模型可以替换。

工程启发：对于浏览器 Agent 产品，run artifact 应成为一等资产；失败后可以直接进入 Diagnose / Replay，而不是只保存聊天文本。

WebPilot GitHub

4. 今天没有新的高价值端侧 AI Runtime 发布：继续把重点放在可归因的 Browser/GPU 遥测

过去 24 小时没有发现比近期 1-bit WebGPU、WebGPU kernel fleet 更高价值的新端侧模型或 Runtime 底座，因此不拿普通模型发布补数量。

工程启发：端侧 AI 下一步很值得借鉴 CrUX attribution 思路：除了 tok/s，还应记录 model load、GPU memory、CPU orchestration、network model bytes、background lifecycle，并能归因到具体 model/kernel/browser milestone。

浏览器技术

CrUX 从页面体验继续深入到子资源 CPU / Network Attribution

新广告指标的测量从主文档 TTFB 后开始，持续到 tab unload；Count/Density 采用 viewport sampling，CPU 与 Network 则从浏览器内部资源和 frame attribution 得到。对浏览器性能工程而言，这比单纯增加一个 dashboard 指标更重要：它证明 field telemetry 可以保留“谁消耗了资源”的语义。

Browser Self-Improvement

今天的新原则：Attribution Before Diagnosis（先归因，再诊断）

过去几期已经逐渐补齐 Persistent Runtime、Semantic Ground Truth、Post-condition Verification、Capability Budget。今天 Chrome 的 CrUX 实践提醒了更靠前的一层：Telemetry 如果不能把异常可靠归因到具体 subsystem / frame / resource / action，后面的自动 Diagnose 很容易只是相关性猜测。

Telemetry / Regression
        ↓
Attribution
├─ component
├─ frame / origin
├─ resource
├─ agent action
└─ model / kernel
        ↓
Attribution confidence gate
        ↓
Diagnose
        ↓
Candidate patch
        ↓

        ↓

        ↓
Canary / Field telemetry
        ↓
Learn

业界走到哪：Chrome 在广告场景已经把真实用户 field telemetry、资源分类和 CPU/network attribution 接起来，并用于理解和干预高资源消耗体验；但它不是 AI 自动 Patch 闭环。

能否迁移：很适合迁移到 Browser Runtime / Agent Harness。Trace Agent 不应该只看到“P95 变慢 12%”，而应得到 attribution evidence；只有归因在多次运行、多个环境中稳定，才启动昂贵的 culprit / bisect / patch Agent。

对 Harness 的启发：Observation schema 应包含 value + attribution + provenance + confidence，而不是只有 value。Learn 时也要保存归因条件，避免把只在某类页面/GPU/版本成立的规律扩散成全局规则。

WebPilot：值得观察的本地 Browser Runtime 样本

WebPilot 的价值主要在工程组合：本地 Ollama、Playwright Chromium/installed browser/CDP、profile 策略、运行记录、smoke test 和版本化 tool schema。当前规模和成熟度仍有限，适合作为 Runtime 架构样本，而不是直接视作 Browser Agent 基础设施标准。

今天的一个判断

Browser Self-Improvement 的 Observe 层不能停在“发现指标变差”，必须继续回答“这次变化到底归因给谁”。

浏览器是多进程、多 frame、多资源、多线程、多 GPU/driver 的系统。没有 attribution，Agent 很容易把相关性当因果关系。今天 Chrome 的 CrUX 广告指标提供了一个很实际的参考：先把真实用户资源消耗分解到可解释对象，再谈自动 Diagnose 和 Improve。

因此近期主线可以继续收敛为：

Persistent Runtime
→ Semantic Ground Truth
→ Context-Bound Capability
→ Post-condition Verification
→ Capability Budget
→ Attribution Ground Truth
→ Diagnose / Verify / Learn

筛选说明：过去 24 小时没有发现达到门槛的新 Firefox / WebKit 正式发布，也没有新的高价值端侧模型 Runtime，因此今天保持较低条目数。
