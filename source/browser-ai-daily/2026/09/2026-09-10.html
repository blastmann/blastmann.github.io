今天最值得看

1. BrowserSkill 0.2.1 把“动作成功”从返回值推进到运行时验证

Tencent BrowserSkill 9 月 9 日发布 0.2.1。最值得关注的不是版本号，而是几项很具体的 Runtime 修复：填表操作在报告成功前会验证实际结果；DeepSeek Harness 插件会同步 observation state；session stop 时修复 agent tab 泄漏、borrowed tab 生命周期与跨扩展 CDP 限制下的导航恢复。

为什么值得关注：Browser Agent 很容易出现一种“假成功”：tool call 返回 success，但页面状态并没有按预期改变。BrowserSkill 这次把 verify 放到动作执行层，而不是交给上层模型自己猜。

工程启发：Browser Runtime 应把 action result 设计成 requested → executed → observed → verified 四个阶段。只有最后一层通过，轨迹才应该进入 Learn / Skill / benchmark。

BrowserSkill CLI 0.2.1 · BrowserSkill Extension 0.2.1

2. Chrome 153 的安全更新里，AI 已经直接进入真实浏览器漏洞发现流水线

Chrome 153 Stable 包含 230 个安全修复。值得单独注意的是，Chrome 官方清单里同时出现了由 Google BigSleep@Grape 报告的高危漏洞，以及由 OpenAI Codex Security 报告的高危 WebPackaging use-after-free；另外 V8 的 CVE-2026-87491 已确认存在在野利用。

为什么值得关注：这里的 AI 已经不是安全报告摘要工具，而是实际进入 Chromium / V8 / Browser Security 的发现链路，并产生可进入正式修复流程的漏洞证据。

Browser Self-Improvement 位置：当前最成熟的是 Observe / Discover → Reproduce / Validate → Triage；后续 Patch、build、Canary 仍主要由传统 Chrome 工程流水线负责。

Chrome Releases：Chrome 153 Stable security fixes

3. SuperSplat 3.0 用 WebGPU 重写编辑器：GPU 不再只是渲染终点，而是数据处理 Runtime

PlayCanvas 9 月 9 日发布 SuperSplat Editor 3.0，编辑器从 renderer 到 data model 都进行了 WebGPU-first 重构。Gaussian 的 projection、frustum culling、compaction、depth sorting 和 draw submission 都在 GPU 上执行，并使用 compute projector、GPU radix sort 与 indirect drawing。

为什么值得关注：这是一类比“WebGPU 跑一个模型 demo”更成熟的浏览器工程实践：大量数据变换、筛选、排序、提交都进入 GPU pipeline，目标是降低内存占用并保持大场景交互响应。

端侧 AI 启发：浏览器内 AI Runtime 也应该把 token/embedding/vision patch 的预处理、筛选、排序、layout 和 dispatch 看成同一条 GPU dataflow，而不是只有 GEMM / attention 才值得 GPU 化。

PlayCanvas：SuperSplat Editor 3.0 Rebuilt on WebGPU

4. 补推 Chrome DevTools MCP 1.9：Agent 能力开始被拆成可关闭、可限制的权限面

9 月 8 日发布的 Chrome DevTools MCP 1.9 没在昨日推送中展开。这个版本加入关闭 JavaScript execution tools 的选项，并进一步让 --no-javascript-evaluation 覆盖 navigation 和 initScripts；同时支持 configurable filesystem roots、关闭 source maps、cookie-debugging skill，并把 trace buffer 默认值调整到 DevTools 的 1.2 GB。

为什么值得关注：Browser Agent 不应该只有“连接 DevTools / 不连接 DevTools”两个状态。真实 Runtime 更需要把 JS execution、filesystem、navigation、trace、source maps 分成独立 capability。

工程启发：以后 Browser Harness 的权限模型更适合用 Tool Group / Capability Set 表达，而不是给 Agent 一整套 CDP 权限。

Chrome DevTools MCP v1.9.0

Chrome 153：安全修复本身也在说明浏览器工程的 AI 入口在哪里

Chrome 153 Stable 一次包含 230 个安全修复，其中涉及 WebGL、ANGLE、GPU、V8、Network、WebUI、DevTools、Extensions、ServiceWorker、FileSystem 等大量组件。对 Browser Self-Improvement 来说，这个列表本身就是一个很好的任务分布：高价值问题往往不是“生成一个新功能”，而是从 crash / sanitizer / fuzz / unusual state 中发现真实缺陷，再把问题压缩到一个可复现、可验证的 component-level case。

Crash / Fuzz / Security signal
        ↓
Candidate issue
        ↓
Reproduce in isolated runtime
        ↓
Component owner / culprit range
        ↓
Patch
        ↓
Regression test
        ↓
Canary / Stable telemetry

这里 AI 最容易先接入的是前半段，因为 discovery、reproduction、triage 都有比较清晰的输入输出；直接自动修改 V8 / GPU / WebGL 则仍需要更强的独立验证。

端侧 AI

WebGPU 工程重点正在从“能运行”转向“整条数据流如何运行”

SuperSplat 3.0 的价值在于，它把 culling、compaction、sorting、indirect draw 都放到了 GPU 上。对端侧 AI，这是一个很好的类比：模型推理的性能并不只由 kernel 决定，CPU ↔ GPU 往返、buffer 生命周期、数据重排、筛选和 dispatch 同样会决定最终延迟。

Input
  ↓
Decode / preprocess
  ↓
GPU-side transform / filter / compact
  ↓
Kernel execution
  ↓
GPU-side postprocess
  ↓
Only small result back to CPU

如果浏览器内 LLM / VLM Runtime 仍然频繁把中间状态拉回 JS，再重新提交给 WebGPU，单个 kernel 的优化很容易被 orchestration overhead 抵消。

浏览器 × AI

BrowserSkill 的 0.2.1 是一个很典型的 Runtime correctness 进展

Browser Agent 工具层常见的错误是把“命令发出去了”当成“动作成功了”。填表尤其容易出问题：框架可能触发了 input event，但 React/Vue controlled state 没更新；元素被替换；页面 debounce 后又恢复旧值；或者 selector 指向了视觉上相似但不是目标的节点。

更稳的 Browser Action 应该是：

Intent
  ↓
Locate target
  ↓
Execute action
  ↓
Read back browser state
  ↓
Compare expected post-condition
  ↓
Verified success / explicit failure

这层验证最好由 Browser Runtime 完成，而不是把 DOM 再丢给 LLM 问“你觉得刚才成功了吗”。

Chrome DevTools MCP 的方向：把 Browser Agent 权限从连接级别拆到能力级别

关闭 JS execution、限制 filesystem root、过滤 Chrome WebUI target、控制 source maps，这些看起来都是零碎 option，但组合起来其实是在形成 Browser Agent 的 capability boundary。

Browser Agent Capability Set
├─ Observe DOM / network / console
├─ Performance trace
├─ JavaScript execution
├─ Navigation
├─ Filesystem access
├─ Source map access
└─ Browser-internal target access

对于本地 Browser Agent，这比“只要连接 localhost MCP 就默认可信”更合理。

Browser Self-Improvement

今天的新判断：Learn 之前必须有 Post-condition Verification

过去几天我们一直在补强 Independent Verification、Runtime Contract Testing、Improvement Integrity 和 Verified Capability Learning。今天 BrowserSkill 的实际修复把一个容易忽略的环节补了出来：单个动作自身也必须验证 post-condition。

Observe
  ↓
Diagnose
  ↓
Action / Patch
  ↓
Post-condition Verification
  ├─ page state changed?
  ├─ expected value persisted?
  ├─ navigation reached target?
  ├─ process / tab lifecycle correct?
  └─ no hidden runtime error?
  ↓
Task-level Verification
  ↓
Canary / Telemetry
  ↓
Learn

否则会出现一个非常危险的闭环：

Tool returns success
      ↓
Agent assumes success
      ↓
Trajectory marked good
      ↓
Skill / Memory learns wrong behavior
      ↓
Future failure becomes systematic

所以 Browser Self-Improvement 里的 Learn，不应该只消费“最终任务成功”的轨迹，还应该要求关键 action 自带 state transition evidence。

Chrome Security：AI 发现真实漏洞已经进入 Browser Self-Improvement 的前半环

Chrome 153 的安全修复清单中出现 BigSleep 与 Codex Security 直接报告的高危 Chromium 漏洞，是今天最强的真实工程信号之一。它说明 AI 已经能在浏览器这种大型 C++ / Rust / GPU / JS Runtime 系统里产出可进入 security triage 的发现。

当前闭环大致是：

AI / fuzz discovery
        ↓
Issue evidence
        ↓
Reproduction / validation
        ↓
Human security triage
        ↓
Patch + conventional CI
        ↓
Stable rollout

下一步真正值得做的不是让 AI 直接自动合入 patch，而是把中间证据标准化：reproducer、affected build range、stack / sanitizer signature、suspect CL range、minimal regression test。这样 Patch Agent 才能接得更稳。

补推 Refine Cycle：小步修改、journal、rollback 比“自动重写 Harness”更可信

本周出现的 Refine Cycle for Hermes Agent 是一个值得跟踪的小型实践：它对跨 session 重复失败做 fingerprint，达到重复阈值后才提出最小 skill / memory 修改；每次 mutation 先 journal，支持 rollback，并限制每天修改数量。作者还明确区分了哪些结论来自测试、哪些还缺生产使用证据。

它最值得迁移到 Browser Harness 的不是具体实现，而是三个约束：重复证据才触发、最小修改、可回滚。

理论侧提醒：更多候选 Patch 不等于更安全地改进

《Safe Harness Self-Evolution》进一步指出，生成 modification 和认证 modification 是两个不同瓶颈；当 evaluation capacity 有限时，生成更多 candidate 并不保证更容易得到可安全采用的更新。越接近性能上限，识别真实小改进需要的评测成本还可能急剧上升。

这对浏览器工程非常现实：一次 0.3% 的 Speedometer / page-load 改善，如果噪声、设备差异和回归面都很大，验证成本可能远大于提出 patch 的成本。

BrowserSkill 0.2.1：值得把 eval 放到 action state transition 上

BrowserSkill 仓库已经带有 evals/browser，并强调 agent-neutral browser capability evaluation。今天的 fill result verification 和 observation synchronization 很适合进一步变成 deterministic eval：给固定页面、固定动作、固定 expected state，不需要 LLM 参与就能判断 Runtime 是否正确。

SuperSplat 3.0：WebGPU 作为浏览器内通用计算底座的成熟案例

与模型 demo 相比，编辑器这种长时间运行、数据频繁变化、交互要求高的应用更能暴露 WebGPU Runtime 的真实工程问题：内存、buffer 生命周期、GPU sorting、indirect draw、CPU/GPU 同步、长场景稳定性。对浏览器端 AI 来说，这类项目值得作为 WebGPU engineering reference。

今天的一个判断

Browser Self-Improvement 现在最应该补的不是“让 Agent 更会改”，而是把每个 Action 和 Patch 都变成可验证的状态变化。只有浏览器 Runtime 能证明“动作真的发生、结果真的保持、没有隐藏错误”，这次成功才有资格进入 Learn。
