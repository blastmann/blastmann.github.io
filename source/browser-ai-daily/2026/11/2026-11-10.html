今天最值得看

1. skild-ai/steel-webgpu：新发布的浏览器 WebGPU 机器人接触求解器（11/09 新仓库 + v0.1.0）

发生了什么：skild-ai/steel-webgpu 于 11 月 9 日 19:36（北京时间）创建，0.1.0 Release 在当日 20:36 发布。它将 Newton 的 SolverSteel（FeatherPGS 关节接触求解器）移到 WebGPU，支持 URDF、MJCF、USDA 场景导入，提供独立核心、three.js 和 React Three Fiber 三种入口，Apache-2.0。

为什么重要：这不是把机器人视频放进网页，而是让浏览器 GPU 计算物理场景。渲染使用 GPU→GPU 位姿拷贝，正常帧无需把姿态读回 CPU；对 WebGPU 端侧复杂计算、GPU 资源同步和实时交互都很有参考价值。

证据与成熟度：有可安装包、示例、测试命令和首个正式版本，属于早期 0.1.0；未找到独立的 Chrome/Safari/移动端正确性对照及可比较的仿真性能数据。工程启发：复杂计算 Runtime 应同时记录 GPU 设备能力、CPU Readback 次数、数值误差和 Frame Pacing，不仅看平均 FPS。包使用说明。

2. browser-tts-benchmark：新开源、保留原始证据的浏览器本地语音基准

发生了什么：browser-tts-benchmark 于 11 月 9 日 13:28（北京时间）创建，为 Google Chrome 中的 CPU/WASM 与 WebGPU 语音生成提供统一的 20,000 字符英文固定负载、固定模型、运行回执、音频样本及可审查的 PR 结果。

为什么重要：过去本地 TTS 常见的问题是把“首音频”、“热推理”、“模型加载”混在一起比较。这个项目明确分开协议，并且把不同协议的历史数据标记为不可直接算加速比。

作者实测：同一台 Apple M1 Pro/16 GiB、Chrome 157 上的 Piper 单人声模型，五次热运行中位耗时从 CPU/WASM 的 170.64 s 到 WebGPU 的 12.07 s（约 14.1×）；计时不包括初始化、哈希及 WAV 保存。合成的是约 1053 秒语音，不是首包耗时或全部模型通用加速；只有一台机器、一种声音、英文，未验证 Safari/Android/音质。工程启发：可直接借鉴其“固定模型 + 相同输入 + 原始回执 + 同协议对照”测试门禁。可审查的实验记录。

3. Playwright：用 Agent 标签把工程任务交给独立执行平台（11/10 已合并）

发生了什么：microsoft/playwright #44019 于 11 月 10 日 07:24（北京时间）合并。维护者给 Issue/PR 标记 agent-triage、agent-implement、agent-task 或 agent-review 后，新的轻量 GitHub Actions 桥接文件会触发 microsoft/devops.playwright.dev 中相应 Agent 流程。桥接流程不检出不可信代码，只负责发起受控任务；旧标签仍暂时保留在原流程中。

为什么重要：这里体现的不是某个 AI 一次修 Bug 的结果，而是大型浏览器测试基础设施正在正式接受 Agent 工程任务，并把“谁授权触发”与“在哪里执行”分开。

边界：已合并的是触发器/路由基础设施，不等于 4 类 Agent 已全部验证质量，也不能声称自动修复和 Canary 闭环已经建成。工程启发：团队可以采用“任务标签/权限 → 隔离执行 → 独立验证 → 候选变更”的架构，不必预设 Agent 必须走固定步骤。

4. LiteRT-LM：修正 NPU 多会话上下文克隆的 KV Cache 隔离（11/10 已合并）

发生了什么：LiteRT-LM #4465 于 11 月 10 日 06:32（北京时间）合并，修复单个 NPU Engine 在多会话克隆上下文时遗漏仅供 Decode 使用的 KV Cache Buffer 的问题。先前从 prefill_input_buffers 拷贝状态可能漏掉真实缓存，某些量化模型还会错误地复制 Float32 占位缓冲，而不是 Int8/Int4 的真正 KV Cache。

为什么重要：这属于端侧多会话状态正确性，而不仅是普通 Bug Fix。多个 Tab、Agent 共享一个本地模型时，不能让 Session A 的缓存状态覆盖 Session B。补丁改为使用 ActiveContextGroup().input_kv_cache_buffers，并检查 Buffer 的类型和维度。

证据边界：PR 已合并；未找到公开的手机多会话 Benchmark 或跨设备发布后反馈。工程启发：对共享模型 Runtime，建立可独立验证的 Clone/Restore 一致性、不串话测试，以及量化与未量化状态的差异检查。

5. llama.cpp WebGPU：语音解码算子回退造成的数量级性能差异（待合并 PR）

发生了什么：llama.cpp #31708 自 11 月 5 日提交，11 月 10 日仍有更新，截至本期尚未合并。它为 WebGPU 新增 COL2IM_1D F32 算子，解决 Qwen3-TTS/PocketTTS 波形解码在 CPU 与 GPU 之间回退和同步的问题。

作者实测：NVIDIA L4 + 原生 WebGPU，16 种正确性用例与 CPU 参考一致；同样的 64 帧完整 TTS、各版本五次交替运行，Qwen3-TTS 0.6B 从 33.299±0.361s 降到 5.676±0.202s（5.87×），PocketTTS 从 1.158s 到 0.838s（1.38×）。模型加载不在计时内，音频字节对照一致。

工程启发：端侧 AI 的大幅改善可能不来自更快 Shader，而来自避免某个算子导致整条执行图反复跨 CPU/GPU。应将 CPU Fallback 次数和总同步时间纳入 Kernel 性能门禁。尚缺：合并、Safari/移动 GPU 复测、真实应用数据；不能称为已正式发布的收益。

端侧 AI

浏览器端从“模型能运行”走向完整操作链路可测量：TTS 基准在相同模型、负载、声音和设备下分离冷/热执行；COL2IM_1D 说明一个 CPU Fallback 就可能改变整条推理图的成本。不同硬件、模型和计时口径的数字不能横向比较。

LiteRT-LM 的 NPU 上下文修订提醒：共享模型的第一优先级是状态正确与隔离，再谈 Prefix/KV Cache 复用。对移动端应该补上多 Session 混合抢占、内存压力、暂停恢复和取消后的状态一致性测试。

浏览器 × AI

Playwright 的 agent-* 标签路由与新出现的 Opera DevTools MCP 从两侧体现“任务与执行环境分离”。前者控制谁可以让 Agent 启动工程工作；后者允许外部 Agent 调用浏览器调试能力。两者都需要操作权限、浏览器 Revision、运行证据和失败恢复；只有能 Click/Fill 远不足以成为生产 Runtime。

浏览器 Agent 的实际任务如果涉及用户已登录 Profile，不应把读到的网页内容直接当成高权限指令。本期还没有公开证据证明新 Opera MCP 通过了独立安全审计。

今天的一个判断

浏览器与端侧 AI 的工程价值正从“新模型更快”转向“能解释哪里快、验证没有变错，并把可复测的结果传递给下一轮 Agent”。 当前最适合团队优先建设的，是可组合的运行证据、性能对照与受控任务执行环境；是否让 AI 自动修改代码，应由后续独立验证能力决定，而不是先建固定工作流。
