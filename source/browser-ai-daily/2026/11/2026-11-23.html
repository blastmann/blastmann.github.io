今天最值得看｜两项七日补推

1. Cloudflare Clairic：多字段并行解码，而非把大模型当 JSON 生成器（11/18 官方发布）

发生了什么：Cloudflare 于 11 月 18 日发布重新设计的 Clairic 27B 和 Clairic-flash 9B，并开放完整权重（Apache-2.0）及本地 Python 加载辅助代码。新的 Clairic 从预览版的单次前向计算改为parallel slot autoregressive generation（并行槽位自回归生成）：每个待抽取字段有独立的输出序列和停止标记，所有字段在同一服务批次里推进。计算、估计、日期和预测使用专门训练的输出头，回应还包含来源字符位置、置信度和空值概率；新版能读取图片与 PDF（合计最多四个图片或页面）。

技术究竟新在哪里：不是新建一个提取 JSON 的 Prompt 包装，而是让受限字段结构直接参与模型的解码调度。相对预览版的单次决策，新版允许文本字段持续生成，同时多个字段并行推进；相对一般 LLM 逐 Token 输出整份 JSON，它返回可单独验收的字段和来源证据。核心并不是“零自回归”——新架构明确使用自回归，只是让各个字段并行而非全部字段串行生成。

可检查证据：Cloudflare 内部评测中，336 个新文本字段预览版答对 295 个，新版 335 个，flash 328 个；96 次文本字段请求中，Clairic-flash 的服务端 HTTP p50/p95 为 155/328 毫秒，27B 为 358/736 毫秒。全部为厂商指定任务、指定服务器的自报数据，不能推断手机或 WebGPU 的延迟；也没有统一公开的提取基准。模型卡可检查 9B 版本基于 Qwen3.5-9B、具有独立的 typed head、权重和请求实现。另有 11/18 的小规模社区 M5 Pro 试验报告 34/34 字段（PyTorch）及 MLX 文本 33/34，但样本量极小、MLX 图片/PDF 路径未正常工作，不能据此推断通用准确率。

技术新颖性：高（面向结构化抽取的并行槽位解码和可追溯字段），值得深入研究：高；值得在手机直接部署：低至中（9B 仍偏大，缺乏移动 NPU/功耗验证）。建议在 Browser Agent 的网页表单、账单和错误日志提取场景，使用同一批网页内容比较 Clairic、通用小模型加 JSON Schema 和规则抽取；同时测字段准确率、漏报率、来源 span 一致性、p50/p95、内存和输入截断。高置信度不等于事实正确，应由程序再核验关键字段。

原始来源：Cloudflare 官方研发文章（11/18）、Clairic-flash 权重、模型卡及代码、Clairic 27B 权重。小样本社区实验：M5 Pro 本地实验数据（未独立复测）。

2. WebMCP Tool 身份：同名工具重注册也不能误调用旧能力（11/19 规范 PR 合并）

发生了什么：Web Machine Learning Community Group 的 WebMCP 提案于 11 月 19 日合并 #348：将原来的 RegisteredTool 字典改成 Tool 接口，底层以每次注册独有的 ID 标识工具，而不是仅按名称匹配。11 月 19 日版本的 WebMCP 社区草案 还规范了跨文档工具执行、生命周期取消以及浏览器侧待执行状态的管理。

技术究竟新在哪里：同一网页可能在登录切换、导航或重新渲染时注销、再注册同名工具。如果 Agent 缓存的是工具名称，而不是注册身份，便可能把旧授权或旧上下文套用到新能力。新 Tool 是一次注册的专属句柄；旧句柄在注销后失效，即使同名工具重新出现也不应成为旧调用的目标。这是典型的执行身份与生命周期正确性问题，不是普通接口重命名。PR 也明确它解决竞态并为 opaque-origin 文档的后续执行能力铺路；后者仍有独立未合并工作，不能写成已经支持。

可验证证据：规范 PR 已合并；草案已经定义 executeTool()、getTools()、AbortSignal、toolcancel、toolactivated 及待执行映射，但社区组草案不是 W3C 正式标准。PR 明确说明新接口对 JSON.stringify(tool)、structuredClone(tool) 等存在兼容性变化。可利用 WebMCP WPT 对同名工具替换、跨 iframe 撤销、页面卸载和并发取消进行复演；本期没有独立跑通这些测试，也没有证明 Chrome、Safari、Firefox 正式一致支持。

技术新颖性：中高（Web 平台工具身份和竞态安全机制），值得深入研究/实测：高。Browser Harness 应把工具注册身份、来源 Frame/Origin、注册版本和生命周期状态一同保存。测试应让旧操作在新工具注册后继续完成或取消，确认无法“借尸还魂”；不可仅凭返回成功就认定真实业务状态已被正确修改。

原始来源：WebMCP #348（11/19 merged）、11/19 WebMCP Draft Community Group Report、Opaque-origin 工具执行的后续问题 #349。

浏览器技术

标准侧：11/19 WebMCP 草案将注册工具的唯一身份、跨 Frame 可见范围、调用取消和卸载状态描述为平台级行为。对于 Chromium、WebKit、Firefox、Edge 乃至任何嵌入式 Browser Runtime，技术价值主要来自正确的权限边界和执行生命周期；不是“多加一个 MCP 接口”。必须以浏览器实际实现和 WPT 作为支持依据，而不是依据规范发布就称各引擎已上线。

其他厂商：本次检查了 Chromium/Chrome、WebKit/Safari、Firefox、Edge、Opera、Brave 的近期原始发布、WebGPU/WASM 和网络/媒体相关线索。没有核实到符合选题门槛且未被前七天日报覆盖的过去 24 小时新架构首发。11/20 W3C WebNN 候选草案更新已在 11/22 日报记录，不重复抬升为新闻。

端侧 AI

Clairic-flash 的开源权重和 Python 推理代码允许在本地服务器或大内存设备做对照；但 9B BF16 权重、图像路径和运行时支持都不等于手机端低成本可部署，更不等于浏览器 WebGPU 原生运行。测试应分别记录模型权重常驻内存、首请求延迟、序列批处理效果和内存峰值。当前未发现经独立核实的 11/22—23 新 NPU 算法或 WebGPU Kernel 首发。

浏览器 × AI

可组合出一种工程实验：网页通过 WebMCP 提供有来源身份的操作，Agent 用类似 Clairic 的结构化抽取从页面、邮件、PDF 获取字段，动作前独立校验字段证据、工具句柄及用户权限，再回读目标页面确认副作用。这只是建议的系统组合，不是 Cloudflare 或 WebMCP 已发布的端到端产品。重点防止同名 Tool 被重注册后误执行，以及从未被证实的字段被带入有副作用的操作。

Browser Self-Improvement

本期未发现新的完整 Observe → Diagnose → Improve → Verify → Learn 自主改进闭环。WebMCP Tool 身份与取消语义可作为 Verify 环节的回归测试用例；Clairic 的字段来源与置信度可为 Observe/Diagnose 产生可检查证据，但两者均不会自动修改 Harness，也不会自动学习。可迁移方法是固定一组跨 Frame / 取消竞态回归，逐次修改 Browser Runtime 后独立重放，保留失败输入与版本；尚缺自动诊断改进、Canary 和跨引擎验证。

今天的一个判断

真正值得跟踪的变化，是把 Agent 不稳定的文字输入和工具名称变成可检查的字段证据与不可混淆的执行身份。本期优先尝试 WebMCP 同名工具重新注册/取消的 WPT 回归；Cloudflare Clairic-flash 适合做网页数据抽取的基准实验，但不能因为有开放权重就直接判断它适合手机端。
