今天最值得看

1. RegenHarness：Self-Improvement 需要一个不可被候选修改的 Verification Root

RegenHarness 面向长时运行 Agent，把 planning、supervision、verification 与 recovery 分离，并强调 Observed Fact 与 Accepted Progress 不能混为一谈。对 Browser Self-Improvement 最值得借鉴的是：Agent 可以持续改 context rules、task templates、routing 与 recovery policy，但决定结果是否可接受的 commit gate 必须独立于被优化对象。

为什么值得关注：浏览器工程里的自动改进最终一定会触及 Prompt、Skill、Harness，甚至 Chromium/V8/Skia 源码。如果 Candidate 同时能够修改自己的 benchmark、阈值或 verifier，就会出现“改答案同时改评分标准”的闭环污染。

工程启发：把 WPT、hidden regression set、security gate、benchmark definition、promotion threshold 做成独立且版本化的 Verification Root；每次实验同时记录 candidate SHA、verifier version、benchmark version、环境与证据。

2. Chrome Connection Allowlists：Browser Runtime 开始承担 AI 代码的网络能力边界

Chrome 的 Connection Allowlists 用严格 allowlist 约束 document / worker 可以连接的 endpoint。其安全动机与动态生成代码、生成式 AI 带来的数据外泄风险直接相关。

为什么值得关注：这不是单纯的 Web 安全 API。AI Native Browser 中，Agent 或生成代码最终都要通过 Browser Runtime 执行；网络、Origin、Credential、Tab 与 Session 权限应该成为 Runtime Policy，而不是由模型自行判断。

工程启发：Browser Agent 的网络能力可以采用 session-scoped endpoint allowlist，并将授权、实际连接和结果写入 audit evidence。

Chrome：Connection Allowlists

3. RA Browser Use：WebGPU / WASM 本地推理开始直接进入 Extension Browser Agent

RA Browser Use 是 Nanobrowser 路线上的 on-device Browser Agent 项目，目标是在 Chrome Extension 内通过 WebAssembly + WebGPU 运行模型，同时保留云模型作为复杂任务的升级路径。项目仍处于 early development，适合观察架构方向，不宜把它视为已经成熟的产品。

为什么值得关注：它把端侧模型从“浏览器里跑一个 LLM demo”推进到真实 Browser Agent loop：页面 observation、本地快速 decision、浏览器 action，再在必要时升级到云端 reasoning。

工程启发：端侧模型更适合 element ranking、action/target、goal/stuck detection、页面变化判断等高频低熵任务；复杂规划再交给云端。

RA Browser Use GitHub

4. AIDE²：Hidden Evaluation + Successive Promotion 是长期 Self-Improvement 的可迁移结构

AIDE² 让 research agent 持续修改自身代码，并通过 hidden evaluation 决定新版本是否晋级。其长期运行过程产生连续改进，并将部分收益迁移到 held-out benchmark。

为什么值得关注：它与近期 RRSI 的方向互补：RRSI 重点防止 Harness evolution 过拟合；AIDE² 展示多代 candidate 通过隐藏评测逐代 promotion；RegenHarness 则强调 verifier / commit gate 与被优化对象隔离。

工程启发：Chromium Self-Improvement 可以采用 candidate → hidden regression → held-out platform/site → successive promotion，而不是一次 benchmark 提升就直接沉淀成长期 Skill。

浏览器技术

Runtime Policy 应成为 Agent 能力层的一部分

Connection Allowlists 提供了一个很具体的方向：浏览器自身可以成为 AI-generated code / Agent action 的 Policy Enforcement Point。未来 Browser Capability Layer 不应只管理 DOM、Tab 和 Tool，还应覆盖网络 endpoint、Credential、JS execution 与跨 Session 能力。

端侧 AI

Local AI 不等于 Local Agent 的全部工作都必须由本地模型完成

RA Browser Use 所代表的合理形态更接近 Hybrid Inference：本地模型处理高频、低熵、隐私敏感的 Browser Decision，云端模型处理低频复杂规划。真正值得测量的是 Observation → Prefill → Decision → Browser Action 的端到端延迟、冷启动、内存、功耗与 Cloud Escalation Rate，而不只是 tok/s。

闭环位置：Verify → Promote → Learn。

核心约束：Candidate 可以修改 Chromium/V8/Skia patch、Skill、Prompt、Router 与 Recovery Policy，但不能在同一改进回合中修改决定自己是否通过的 WPT ground truth、hidden regression set、security gate、benchmark threshold 或 promotion policy。

迁移到 Chromium：Verifier 应独立部署和版本化。实验资产至少包含 candidate SHA、verifier version、benchmark version、browser milestone、OS/GPU/driver、运行证据与最终 decision。这样 verifier 升级后，历史实验仍然可以重放与重新判定。

开源与论文 / 工程实践

把 RRSI、AIDE² 与 RegenHarness 拼成一个更完整的 Harness Evolution Gate

RRSI
→ 控制 mutation scope
→ 防 benchmark overfit
→ 保存 rejected edits

AIDE²
→ hidden evaluation
→ successive promotion
→ held-out transfer

RegenHarness
→ independent verifier
→ version-bound commit
→ immutable acceptance boundary

这三类工作组合后，比“让 Agent 自动改自己的 prompt”更接近真实 Browser Engineering：修改范围受控、评测不可见、验收根独立、失败实验保留、通过后再进入 Canary 与长期 Learn。

今天的一个判断

Browser Self-Improvement 真正的“自我”应该有明确边界：策略、Skill、代码和 Harness 可以持续变化；决定这些变化是否可信的 Verification Root 应独立存在。

近期主线正在逐渐形成一套工程上可执行的约束：RRSI 防止 Agent 把自己优化成固定 benchmark 专用系统；AIDE² 用 hidden evaluation 和 successive promotion 检查跨代收益；RegenHarness 再补上“不能通过降低考试难度证明自己进步”。浏览器工程已有 WPT、独立 benchmark、Code Review、Canary 与 Telemetry，现在更重要的是把它们编码成 Agent Harness 的信任边界。
