浏览器 × 端侧 AI 日报

今天最值得看的不是新的浏览器 UI，而是 WebGPU 推理基础设施开始具备“可版本化、可测试、可 benchmark、可从真实设备持续收集证据”的工程形态；同时，端云协同从模型路由推进到本地隐私门、专用推理 Runtime 与可审计策略。

2026-09-02 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

WebGPULocal AI

Hugging Face 发布 207 个 WebGPU kernels，并用 Fleet 收集真实设备性能证据

Hugging Face WebAI 团队在 9 月 1 日发布 @huggingface/kernels：首批 207 个 WebGPU kernel，每个 kernel 都独立版本化，并携带 manifest、正确性测试、benchmark case、WGSL 模板与 provenance metadata。配套的 Fleet 可以直接在浏览器里跑 correctness/performance 测试，并在用户同意后匿名贡献设备结果。

为什么值得关注：这不是“又一个 WebGPU demo”，而是把低层 GPU operation 变成了工程资产。官方在 Apple M4 上对 809 个可比 case 测得相对 ORT WebGPU 几何平均 2.57×、中位数 1.90×，但更重要的是结果可以跨设备、浏览器和 driver 持续验证。

Hugging Face 官方博客

Hybrid ComputePrivacy Gate

Perplexity Hybrid Compute：云上规划，本地处理隐私文件与设备动作

Perplexity 在 9 月 1 日上线 Mac 版 Hybrid Compute。Computer 仍可由云端 frontier model 负责研究、推理和规划，但本地模型处理私有文件、敏感信息和 on-device action。真正决定数据能否离开设备的是 Mac 上的 Privacy Gate：它可以保留本地、掩码、拒绝或请求用户许可。

浏览器 × AI 启发：端云协同不应该只是“按算力选模型”，而应把数据敏感度与操作权限一起作为 Router 输入。Browser Agent 也应让页面数据在进入云模型前经过本地 Policy/Privacy Gate。

Perplexity 官方

On-device ModelPII

PII-Tracer：0.6B 本地模型专门守住端云边界

Perplexity 同日公布 PII-TRACE benchmark 与 PII-Tracer，一个约 0.6B 的本地 PII 检测模型，目标不是通用聊天，而是在长对话和多语言场景里持续发现敏感片段。它输出的信号由应用层执行：保持本地、脱敏后上云，或请求授权。

为什么值得关注：这是非常具体的“Local Small Model as Control Plane”。小模型的价值不一定是替代云端大模型，而是承担隐私、权限、路由和安全判断这种低延迟、必须本地完成的控制任务。

Perplexity Research

Self-ImprovementHarness

补推：AutoSaddler 从失败轨迹诊断 Harness，并用验证集筛掉“只修一个 case”的改动

Microsoft 等团队上周发布 AutoSaddler，把 Harness 优化当作离线学习：从 mini-batch 的失败 execution trace 做深入诊断，对 prompt、tool 和 middleware 生成结构化 patch，然后用 validation set 决定是否接受。论文报告在 GAIA2、SWE-Bench Pro、Terminal-Bench 2.0 上较 base harness 分别提高 9.0、9.6、10.0 个百分点。

Browser Self-Improvement 启发：这比“Agent 反思后改 prompt”更接近真实浏览器工程：先把 failure trace 变成 diagnosis，再只改最小 Harness 单元，最后必须经过独立验证集，防止为单一回归过拟合。

arXiv

浏览器技术

过去 24 小时没有值得单独推送的 Chromium / WebKit / Firefox 引擎级发布

本轮检查了 Chrome for Developers、WebKit 官方更新与 Firefox/Mozilla 相关来源，没有发现比今天 WebGPU kernel / Hybrid Runtime 更高价值、且确实发生在过去 24 小时的新引擎能力。这里不拿普通版本日志填充。

但有一个长期变化值得继续看：WebGPU 的性能问题正在从“浏览器有没有 API”转向“同一个 operation 在不同 GPU / driver / browser 上如何持续选择最佳实现”。这会让浏览器端 AI 的竞争点从 API availability 下沉到 kernel、编译、缓存、调度与设备特征选择。

端侧 AI

Lily：为 Apple Silicon + Qwen3.6 做专用 Runtime

Perplexity 还公布了 Lily，本地推理引擎直接以 Rust runtime + 自定义 Metal kernels 执行 Qwen3.6-35B-A3B，不经过 PyTorch 或 MLX-LM。它把 prefill 与 decode 分开优化，并围绕固定模型结构协调 kernel、数据移动与 scheduling。

Perplexity 官方

端侧优化开始从“通用 Runtime”出现专用化分层

Hugging Face 选择将 operation kernel 独立出来，Perplexity 则针对具体模型与 Apple Silicon 做端到端专用 Runtime。两者方向不同，但都说明一个问题：当端侧模型进入产品化阶段，真正决定体验的是 kernel、内存布局、调度与设备差异，而不是模型参数量本身。

浏览器 × AI

Fleet 让浏览器成为 AI Runtime 的真实硬件测试场

Fleet 的设计很值得 Browser Runtime 直接借鉴：测试在用户浏览器的真实 GPU/driver 环境里执行，结果既包含 correctness，也包含 performance。每个 kernel 本身又带有明确 contract 和 benchmark case，所以线上设备结果可以反过来指导 variant selection 与后续优化。

产品启发：端侧 Browser AI 最终需要类似“设备画像 + workload shape + kernel variant”的 Router。仅仅判断 navigator.gpu 是否存在远远不够。

Hybrid Compute 给 Browser Agent 一个更现实的端云划分方式

Browser Self-Improvement

今天最值得迁移的闭环：让“可优化单元”自带证据

Hugging Face 的 kernel artifact 天然带着 contract、test、benchmark、version 与 provenance；Fleet 再补上真实设备 evidence。它已经非常接近浏览器工程里理想的 Self-Improvement 单元。

Observe
Real-device correctness / perf evidence
          ↓
Diagnose
GPU / driver / browser / shape-specific slow path
          ↓
Improve
New kernel variant / parameter / scheduling choice
          ↓
Verify
Correctness cases + benchmark + Fleet
          ↓
Learn
Update variant-selection rule + retain evidence
          ↓
Revalidate
New browser / driver / GPU arrives
闭环走到哪：今天的 WebGPU Fleet 已经覆盖 Observe → Verify → Learn 的大半，而且 Improve 对象是实际可发布的 kernel variant，不只是 Prompt。它缺少的是自动生成/修改 kernel 的 Agent，但数据和验证基础已经具备。

AutoSaddler 补的是 Diagnose → Patch → Verify

AutoSaddler 解决的正是另一半：从失败 trace 做深入 diagnosis，把 Harness 当成代码生成 targeted patch，并在独立 validation set 上筛选。把这两种思路结合，Browser Self-Improvement 可以形成更完整的工程结构：

Regression / Fleet / Telemetry
          ↓
Evidence-backed Diagnosis
          ↓
Targeted Patch
Code / Skill / Harness / Kernel Variant
          ↓
Contract Tests + Benchmark
          ↓
Cross-device / Cross-platform Validation
          ↓
Accept / Reject
          ↓
Rule / Skill / Variant Selection Update
新原则：不要只要求“改动有测试”，而应要求每个可自我改进单元都是 Evidence-Carrying Artifact：它自己携带适用范围、正确性 case、性能 benchmark、版本、来源和最近一次验证结果。

今天的一个判断

Browser Self-Improvement 真正能落地，关键不是先让 Agent 自己改 Chromium，而是把浏览器工程里的每个“可优化对象”改造成可验证资产。Hugging Face 今天的 WebGPU kernel 结构给了一个很具体的模板：

Artifact
├─ Scope / Contract
├─ Version
├─ Provenance
├─ Correctness Cases
├─ Benchmark Cases
├─ Candidate Variants
├─ Last Verified Environment
└─ Real-world Evidence

然后 Agent 才有条件安全地做 Diagnose、生成候选 Patch，再交给 benchmark、Fleet、多平台回归和 Canary 去决定是否接受。

因此今天新增到 Browser Self-Improvement 主线的关键词是：Evidence-Carrying Artifact（携带证据的工程资产）。

它把之前的 Evidence-backed、Executable、Reviewable、Privilege-preserving、Selective Learning、Knowledge Compilation 进一步落到了一个能直接进工程仓库的具体对象上。

筛选原则：优先官方来源、原始论文与开源项目；过去 24 小时不足时只补过去一周尚未推送且能进入真实浏览器工程闭环的内容。
