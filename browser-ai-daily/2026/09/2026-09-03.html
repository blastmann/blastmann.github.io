浏览器 × 端侧 AI 日报

今天最值得看的不是新模型，而是 Browser Agent 的本地桥接边界和 Browser Self-Improvement 的长期执行结构开始变得更具体：Chrome 154 给 WebSocket → localhost 增加显式地址空间与权限语义；Harness-of-Harness 则把长期改进拆成 Planner / Developer / QA 三个稳定角色，并把验证证据带入下一轮。

2026-09-03 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

Chrome 154Local Agent Bridge

Chrome 154 Beta：WebSocket 正式进入 Local Network Access 权限模型

Chrome 154 Beta 在 9 月 2 日加入 WebSocketInit options bag，并支持 targetAddressSpace。网页可以明确声明 WebSocket 目标是 local 或 loopback；浏览器随后执行 Local Network Access 权限检查，hostname 也必须实际解析到相应的本地地址。

为什么值得关注：大量 Browser Agent / MCP / 本地 Harness 都采用“网页或扩展 → localhost WebSocket → Agent Bridge”。Chrome 正把这条链路从模糊的 localhost 特例，推进成浏览器可理解、可授权、可阻断的能力边界。未来 Browser Capability Layer 不应该绕过浏览器权限模型，而应该利用它。

Chrome for Developers

Self-ImprovementHarness

Harness-of-Harness：用稳定角色和独立 QA 支撑 70+ 轮持续改进

9 月 2 日公开的 Harness-of-Harness（HoH）在现有 coding-agent harness 外再加一层长期执行框架：Project Planner 只规划，Developer 修改产物，QA Tester 只读验证。每一轮的 artifact 与 evidence bundle 成为下一轮的输入。

关键点：它没有要求 Agent 按固定推理流程工作，而是约束“必须产出可验证结果”；实现期测试和独立评估分开，并保留版本化项目历史。论文报告三组 harness-model pair 在三轮后平均相对提升 52.25%，长期案例运行超过 70 轮。

arXiv · GitHub

Firefox 155Automation

补推 Firefox 155：WebDriver BiDi 与 DevTools 并行冲突继续被清理

Firefox 155 修复了 moz:debugging 模块对 DevTools 嵌套事件循环的依赖，避免 WebDriver BiDi 与 DevTools 并行使用时发生冲突；还修复 frame reload 和部分 Actions API 语义。它同时加入 WebAssembly compact import section、wide arithmetic，以及桌面 WebGPU dual-source blending。

Browser Agent 启发：当 Agent 同时使用自动化协议、DevTools、性能分析和页面调试时，“多个控制面能否同时存在”会成为真实稳定性问题。Browser Harness 的验证项应该覆盖并发控制面，而不只测试单一 click/type 成功率。

MDN / Mozilla

Local AIPrivacy

ChatPanel 更新继续验证：本地模型 + Local Bridge + PII Gate 正在合流

9 月 2 日更新的 ChatPanel 把私有浏览器模型、当前页/多 Tab 上下文、本地 Agent Bridge 和可选 PII redaction 放在同一扩展里；本地桥使用 127.0.0.1，云模型只接收用户选择发送的上下文。

为什么只作为产品信号：它不是浏览器厂商或底层标准，但和近期 Agtweb、Runbook AI、ChromeBoost 的方向一致：Browser Agent 正从“远端云浏览器”回到用户真实浏览器，并在本地增加 Privacy / Capability Gate。

Chrome Web Store

浏览器技术

Chrome 154 的 targetAddressSpace 对本地 Browser Bridge 很关键

以前本地 Agent Bridge 常见做法是网页直接访问 ws://127.0.0.1 或一个解析到私网地址的 hostname。Chrome 154 允许在 WebSocket 构造器里显式标注目标地址空间，同时要求安全上下文和 Local Network Access 用户许可。

Public Web App
    ↓ WebSocket(..., { targetAddressSpace: "local" })
Chrome Local Network Access Gate
    ↓ user permission + DNS/address check
localhost / LAN Agent Bridge
    ↓
Local Model / MCP / Browser Harness
工程含义：Ghost Browser 这类产品若需要“网页 ↔ 本地 Agent”通道，应该把权限设计建立在浏览器原生 LNA 之上；更理想的是 Extension / Native Messaging 继续承担高权限操作，而普通网页只拿到更窄的 localhost capability。

Chrome 154 同时继续下沉 WebGPU / Worker 能力

Chrome 154 给 WGSL @builtin(frag_depth) 增加 less/greater 修饰符，以保留 early-Z 优化；同时把更多 CSS Typed OM 构造器暴露给 Worker。前者不是 AI 推理功能，但反映 WebGPU 仍在持续补足精细性能控制。

端侧 AI

过去 24 小时没有发现比昨日 WebGPU kernels / Hybrid Compute 更强的新端侧底座发布

本轮没有用普通模型发布填充。更值得继续跟踪的仍是昨天的两条主线：一是 WebGPU kernel 变成可版本化、可 benchmark 的工程资产；二是 Local Small Model 被放到 Privacy / Policy / Routing control plane，而不是只承担聊天生成。

浏览器 × AI

本地 Browser Bridge 正进入“浏览器原生权限可见”的阶段

过去几天看到的 Agtweb、Runbook AI、ChromeBoost、ChatPanel 都依赖 localhost / Native Messaging / Extension bridge。Chrome 154 的变化说明浏览器本身正在更明确地区分 public、local、loopback 地址空间。

Agent Request
    ↓
Page / Extension
    ↓
Capability Gate
    ├─ Tab / Origin
    ├─ Operation
    ├─ Local Network
    └─ Sensitive Data
    ↓
Local Bridge
    ↓
Real Browser Session
产品启发：不要把 localhost 当成“天然可信”。真正可扩展的 Browser Agent Runtime 应该同时标记来源页面、目标地址空间、操作类型与数据敏感度。

Browser Self-Improvement

今天的新关键词：Independent Verification Loop（独立验证环）

HoH 最值得迁移到浏览器工程的不是多 Agent 数量，而是 Planner / Developer / QA 的权限和职责分离。QA Tester 不改产物，只执行并记录证据；上一轮 evidence bundle 再交给下一轮 Planner。

Telemetry / Regression
        ↓
Planner
读取问题 + 上一轮 Evidence
只生成最小改进计划
        ↓
Developer
Patch / Harness / Skill
        ↓
Independent QA
Build / WPT / Benchmark / Trace
只验证，不改代码
        ↓
Evidence Bundle
Pass / Fail / Perf Delta / Repro
        ↓
Versioned History
        ↓
Next Iteration
闭环走到哪：HoH 覆盖 Plan → Patch → Test → Evidence → Learn/Next Loop，并证明几十轮长时间运行可行；它缺少 Chromium 级 Telemetry 触发、Pinpoint/bisect、Canary 和线上回流，因此还不是完整 Browser Self-Improvement，但非常适合作为中间的执行 Harness。

迁移到 Chromium 时，我会把“角色”换成权限边界

Browser 工程不需要真的启动三个拟人 Agent，重点是让同一个系统也不能跨越职责边界：

Diagnosis Context  → read-only traces / source
Patch Capability   → code workspace only
Verification       → clean build + benchmark env
Rollout            → separate approval / canary gate
Learning           → only evidence-backed artifacts

这样能进一步接上此前形成的原则：Memory Hygiene → Executable Learning → Reviewable Improvement → Trusted Learning → Privilege-Preserving Learning → Selective Learning → Knowledge Compilation → Evidence-Carrying Artifact。

新的补充：Evidence 不能由修改代码的同一执行单元自证。对性能回归尤其如此：Patch Agent 可以给出假设，但 benchmark、trace comparison 和 regression gate 应由隔离环境重新执行。

今天的一个判断

Browser Self-Improvement 的下一步，不是更多自治，而是更强的验证隔离

过去一周的线索正在收敛：经验要筛选，Knowledge 要与 Skill 分开，可执行资产要自带 benchmark 和 provenance；今天 HoH 又补上“验证者不修改产物”。

Observe
  ↓
Diagnose
  ↓
Patch
  ↓
Independent Verify
  ↓
Evidence Bundle
  ↓
Trust / Review Gate
  ↓
Canary
  ↓
Learn
  ↓
Revalidate

如果把这个结构放进 Chromium，我会优先让 Agent 自动改 Harness、测试、benchmark 配置、小范围代码，并把独立 build/benchmark/trace verifier 作为不可绕过的边界。真正的 Recursive Improvement 应发生在这套证据闭环之上，而不是让同一个 Agent“改完以后自己说通过了”。
