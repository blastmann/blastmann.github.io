今天最值得看

1. WebsiteBench：让 Agent 通过真实浏览器探索，重建整套网站

发生了什么：斯坦福 TIGER-AI-Lab 于 11 月 4 日 20:58（北京）创建开源项目 WebsiteBench（Apache-2.0）。它要求 Agent 先通过浏览器探索一个已有网站，再重建外观与行为。公开代码集成 Harbor 任务运行器，提供 Docker 任务包、参考应用和独立的验证脚本；开发文档介绍了用 oracle（参考解）自检、再调用 Codex 等 Agent 跑任务的流程。验证阶段使用 no-network，以减少依赖外部网站变化。资料集入口：WBArtifacts。

为什么值得关注：与只问 Agent “能不能完成点击任务”不同，它测量对真实网站结构、状态和交互的理解能否转化成可运行的交付物。成熟度：11 月 4 日新开源评测基建；本次未复测任务，也未见可引用的独立成功率，不把 README 的功能声明写成已验证的模型能力。

工程启发：Browser Self-Improvement 可以沿用“目标站点冻结版本 → Agent 探索 → 产物构建 → 独立 Oracle 在无外网环境验证”的设计；尤其适合测试 Browser Agent 是否真正理解 SPA 状态、表单验证和跨页流程。运行与 Oracle 说明。

2. Google Three-Live：不直接执行 AI 生成的 3D 代码，而是隔离编译成可移植资产

发生了什么：Google Open Source 于 11 月 3 日介绍 Three-Live（过去 7 天补推）。项目早在 10 月 2 日创建，11 月 3 日是官方公开宣发，并非新仓库首发；11 月 5 日 07:11（北京）发布了 v1.2.3。它让 AI 生成的 Three.js 在受控环境中运行和序列化为 GLB/USDZ 等 3D 资产，Web 使用受限 Worker 路径，原生端通过 Rust/Boa 执行并对接 Android Filament、Apple RealityKit；另有 WebXR、交互插件和 浏览器 Playground。官方明确标记为 Developer Preview、不是正式支持的 Google 产品。

为什么值得关注：它采用“不可信动态代码 → 受控执行/编译 → 数据资产 → 浏览器或原生渲染”的边界，而不是持续给网页中运行的 Agent 任意 JS 权限。它还回应了 iOS WKWebView 不具备通用 WebXR 能力的问题。源码提供 Web、Android 与 iOS 的 SDK，但安全隔离边界仍需外部审计。

工程启发：对 AI Native Browser，值得把模型输出转换为可验证、可缓存、可审计的 数据产物，再交给拥有明确权限的 Runtime 执行；尤其适用于动态图表、交互组件和 3D 内容，而不是直接注入页面脚本。官方介绍。

3. Chrome 157：213 项安全修复，部分漏洞发现明确记录了 Claude / Codex Security 辅助

发生了什么：Google 于 11 月 3 日将 Chrome 157 晋级 Stable（过去 7 天未报的重要官方进展），列出213 项安全修复。其官方公告明确将 Dawn 两项缓冲区溢出、ANGLE 内存问题、WebGL 以及 Prerender 等列为严重漏洞；CVE-2026-121035（Prerender UAF）由 Anthropic 的研究者提交且标注 Claude 辅助；公告还列出数项由 OpenAI Codex Security 或 Claude 辅助发现的 PDFium、V8、SVG、Performance APIs 问题。这是漏洞发现与报告阶段的公开证据，不是 AI 自动修改 Chromium 并完成 Canary 的证据。Google 原始安全公告。

为什么值得关注：相比泛泛 AI Coding 宣传，真实漏洞编号、组件、报告人、修复版本和发布渠道构成了可审计的安全结果；对 WebGPU Runtime 尤其需要关注 Dawn 与 ANGLE 的边界。本期还有 11 月 4 日 Chrome 158 Windows 小范围 Early Stable（158.0.8127.18/.19），以及 158 跨桌面/Android/iOS Beta 更新；不要将 Early Stable 误写成所有用户已升级。官方发布流。

工程启发：构建 Crash / Fuzzer / Sanitizer → Agent 定位 → 最小复现 → Patch → 多平台安全回归 → Canary 的证据链时，必须分别衡量 AI 发现率、误报、修复正确率和发布后风险。不能用“AI 参与报告”直接推断已经具有工程自进化能力。

4. Ink Static Embeddings：把小型静态 Embedding 编译到 JS、Rust/WASM 和 WebGPU，并保留失败的实验

发生了什么：siliconjungle/ink-static-embeddings 于 11 月 4 日 11:14（北京）创建。它支持 Model2Vec 和 Sentence Transformers 的 StaticEmbedding 格式，针对词向量查表、均值池化和可选 L2 归一化生成 JS、Rust、Rust/WASM、WebGPU 路径；不支持任意 Transformer/LLM。项目包含三种预训练模型、两个合成样例的跨后端正确性检查和实验报告。

作者的实测：在 Potion 2M 的公开 API 混合语料上，JS 优化从 17.34 降到 9.90 微秒/次（约 1.75 倍）；同一项目报告，NumPy 对照为 8.72 微秒/次，仍快于该 JS 路径。另一项 batch=1024 的 GPU typed-result 优化从 3.50 到 1.70 微秒/Embedding（约 2.06 倍），与 JS 结果不是同一测试。一个自动调优候选虽然在校准集达到 2.63 倍，仍因独立留出集未达门槛而保留原基线。这些都是作者数据，完整分发 CI 部分仍排队。

工程启发：浏览器书签/历史语义查询可以比较静态 Embedding 与小型 Transformer 的内存、启动、精度。更值得迁移的是“候选优化不能通过留出集，就不修改正式选型策略”的验证门禁。实验进度与失败记录。

5. Google GKE Workspaces：端云协同的持久化 Agent 工作台与隔离子任务

发生了什么：Google Open Source 于 11 月 4 日发布 GKE Workspaces 技术介绍，基于 Apache-2.0 的 Kubeflow Workspaces，支持云端持久化浏览器 IDE/JupyterLab、GPU/TPU 资源选择、暂停/恢复，以及从本地 Coding Agent 通过短期可撤销链接调用云端资源。其文章还给出把子 Agent 放到独立容器沙箱、输出候选 Patch 供主工作区审阅的方案。Google Open Source 公开发布页可查看原始代码仓库入口。

为什么值得关注：Browser Engineering 的 GPU Benchmark、Chromium 构建以及多 Agent 并行验证受本地机器资源限制。它提供了持久工作台 + 弹性计算 + 受控子任务的具体系统结构。边界：这属于 Google Cloud/GKE 方案，不是纯端侧、不代表浏览器原生支持这些能力，也没有公布对浏览器编译耗时的独立对照。

工程启发：可借鉴“开发会话长寿命，实验沙箱短寿命，产物必须带回可审查 Patch + Benchmark Receipt”的调度方式；优先考虑成本、凭据边界和结果复现。

浏览器技术

Chrome：11 月 4 日发布 158 Beta（Windows/macOS/Linux、Android、iOS），Windows 另开始小比例 Early Stable；11 月 3 日 Chrome 157 Stable 的 213 项安全修复中，Dawn/WebGPU、ANGLE、V8、PDFium 和导航等组件需要纳入回归重点。Chrome Releases。

WebKit / Firefox：本窗口未核实到足以独立成篇的新架构发布，故不重复旧消息。对跨端项目尤其应追踪 Safari/WKWebView 的 WebXR 限制及 WebGPU WGSL/设备支持差异，不将单项目 README 当成浏览器官方承诺。

Web API / 性能：新的 Three-Live 提供了浏览器与原生渲染边界的具体实践；open-source-hands则演示 Camera + MediaPipe 本地推理、输入去抖与合成手势测试的组合，具备端内可观测和自动化验证价值。

端侧 AI

本期更值得研究的是小型静态 Embedding 的跨后端可移植性：对语义搜索、书签召回、历史记录匹配，先判断低成本查表模型是否足够，再考虑 0.6B 级别的复杂模型。指标至少包含首用下载、模型占内存、冷/热启动、查询 P95、语义召回准确率，以及页面在后台后的恢复行为。项目和测试。

浏览器 × AI

Three-Live 的启发是：AI 产物与浏览器执行能力之间需要一个可以测试和限制的接口。WebsiteBench 则从另一侧验证 Agent 是否真的理解网页。两者结合，可以形成“生成内容 → 隔离运行 → 验证呈现和交互结果”的验证流程。WebsiteBench · Three-Live。

tamesu值得纳入观察：它把 Browser、MCP、Web API、实时音频等不同目标映射到统一 YAML 测试和断言，支持重放、重复运行、P95 门槛、已知波动隔离以及对 LLM Judge 的人工标注校准。不过目前属于作者的开源实现，不代表其各目标已有生产级覆盖。

推荐工程实验：从一个可冻结的站点任务出发，记录 Browser Revision、Playwright/CDP Trace、HTML/DOM 状态与用户动作；分别交给 Agent 生成回归测试或候选修复；在不共享 Agent 会话的独立环境里运行；将结果标成正确、失败、条件性成功和性能退化。仅当功能测试与性能门槛均通过，才将新 Skill / Harness 规则合入共享库；历史失败样本长期重放。

本期结论：没有新的可信证据表明 Chromium、WebKit 或 Firefox 已实现由 AI 独立完成 Telemetry → Patch → Build → Benchmark → Canary → Learn 的完整自主闭环。Chrome 157 的 AI 安全发现和 Ink 的拒绝门禁分别覆盖真实发现与防止错误学习两种重要能力，但不是同一套现成系统。

今天的一个判断

浏览器自我改进的关键不是生成更多 Patch，而是将发现和改进变成可重复验证的证据。WebsiteBench 提供独立运行环境，Chrome 157 展示 AI 辅助真实安全发现的成果，Ink 的反例说明“跑出一次加速”还不足以升级正式策略。适合短期落地的组合是真实任务探索 → 独立 Oracle → 受控候选修改 → 留出集回归 → 结果记录与规则晋级，不要在缺少验证时宣称闭环完成。
