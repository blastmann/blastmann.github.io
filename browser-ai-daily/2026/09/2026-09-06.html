浏览器 × 端侧 AI 日报

周末过去 24 小时没有足够高价值的 Chrome / WebKit / Firefox 引擎级发布。今天不凑数量，重点补推两条本周尚未覆盖、却与 Browser Self-Improvement 非常贴近的进展：Chrome Security 已把 V8 的 AI 漏洞发现推进到自动验证流水线；Web Agent 研究则开始只依靠可观测执行轨迹提前判断任务是否正在失败。

2026-09-06 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

Chromium SecuritySelf-Improvement

Chrome Security：Big Sleep 已成为 V8 的全自动漏洞发现与验证流水线

Chrome Security 2026 Q2 更新披露，V8 新增了用于区分实验环境与生产问题的测试模式，使内部 bug-finding agent 能自动验证发现，确保只报告真实漏洞；因此 Big Sleep 已经以 fully automated pipeline 的形式帮助保护 V8。

为什么值得关注：这不是“AI 帮忙找 bug”的概念演示，而是 Browser Self-Improvement 中已经落地的 Observe / Diagnose → Reproduce → Validate → Route。关键进步是 Agent 的发现必须先通过确定性的浏览器工程验证接口，而不是直接进入人工 triage。

Chromium Security Q2 2026

Web AgentObserve

只看执行轨迹，也能提前判断 Web Agent 是否正在走向失败

Monitoring Web Agents Without Internal Signals 不依赖 token logits 等模型内部信号，而是从 Agent 与网页交互的外部轨迹构建 Macro / Micro 特征，定位第一个未被后续恢复、并最终导致失败的关键错误点。论文在 WebArena-Lite 与 Online Mind2Web 上发现，这类可观测信号可达到接近内部信号基线的风险预测能力，并支持提前干预。

对浏览器工程的启发：Browser Runtime 不必理解模型内部状态，也可以从 action、DOM/AXTree 变化、navigation、error、retry、timeout 和预期状态差异中建立独立 watchdog。它很适合放在 Agent Harness 外侧，做低成本 Observe 与早停。

arXiv:2609.02057

Rendering-in-the-LoopVerify

RILA：把真实浏览器执行反馈放进“生成 → 验证 → 再修改”循环

Rendering-in-the-Loop 不再只用截图相似度评价生成网页，而是让 Agent 在浏览器中重放参考交互轨迹，通过 Action Interaction Verification 收集真实执行反馈，再用同时考虑交互正确性与视觉一致性的评分指导下一轮修改。

值得迁移的点：对 Browser Agent / Extension / WebUI 开发，验证目标应该从“页面看起来对”提升到“交互轨迹在真实 Runtime 里语义正确”。这与昨天 Chrome Extension Agent Verification 正好接上。

arXiv:2609.02088

Dynamic HarnessRuntime Semantics

CordisBench：Harness 能自改之后，生命周期与依赖语义成为新的可靠性问题

CordisBench 用 1,200 个问题评估模型是否能正确推理动态 Agent Harness 中组件依赖、teardown 顺序、cleanup 与 reconfiguration。随着相关组件交互从 2 个增加到 16、24、32 个，模型明显更容易在最终状态和清理顺序上出错。

Browser Runtime 启发：如果未来 Agent 能安装/卸载 Browser Skill、Extension helper、Trace analyzer 或 MCP capability，就不能让模型单靠自然语言推理生命周期。依赖图、cleanup、权限释放和最终状态最好交给确定性 Runtime semantics。

arXiv:2609.01600

浏览器技术

Chrome Security 正在把 AI 引入真实 Browser Bug Lifecycle，而不是只放在代码生成端

Q2 更新透露了几条可以直接映射到浏览器工程闭环的动作：安全报告先在隔离基础设施中复现和补充信息，再自动判断严重性并路由；V8 提供确定性的 crash/testing mode 给 bug-finding agent 做自动验证；Chrome 还在通过 Crowbar 推动约 1700 个第三方依赖进入受管理的自动更新路径。

Bug / Crash / Fuzz finding
        ↓
Isolated Reproduction
        ↓
Deterministic + AI Triage
        ↓
V8 Testing / Validation Mode
        ↓
Real Bug?
   ├─ No → discard
   └─ Yes → severity + owner routing
        ↓
Human / Engineering Fix

这已经非常接近 Browser Self-Improvement 的前半段，只是 Patch → Build → Benchmark → Canary 目前仍主要由传统工程流程完成。

过去 24 小时没有出现比本周 WebGPU kernels、真实设备 Fleet、Hybrid Compute 和本地 Privacy Gate 更强的新进展。端侧主线仍然是：小模型承担筛选、路由、隐私和 verifier；高性能推理继续依赖 WebGPU / Metal 专用 kernel 与真实设备验证。

浏览器 × AI

Browser Agent 需要一个独立于模型的 Runtime Watchdog

“可观测轨迹监控”给 Browser Agent 一个很实用的架构方向：不要等模型自己意识到失败，而是在 Harness 外侧建立低成本的状态检查器。

Agent Intent
    ↓
Action
    ↓
Browser Runtime
    ↓
Observable Signals
├─ DOM / AXTree delta
├─ navigation / frame state
├─ console / network error
├─ retry / timeout pattern
├─ expected-state mismatch
└─ repeated no-op action
    ↓
Risk Predictor / Rules
    ↓
Continue / Retry / Escalate / Stop

这套机制还能直接复用到真实用户浏览器：它只观察浏览器事件和 Agent action，不需要读取模型 logits，也更容易做跨模型统一治理。

Browser Self-Improvement

今天的新关键词：Self-Validating Discovery（自验证发现）

前几天我们强调 Independent Verification：修改者不能自己宣布修改成功。今天 Chrome Security 又补了一层——连“发现问题”本身也需要验证。

Telemetry / Fuzz / Agent Discovery
            ↓
Candidate Issue
            ↓
Reproduce in Isolated Runtime
            ↓
Deterministic Validation Contract
            ↓
Confirmed Issue
            ↓
Diagnosis / Patch
            ↓
Independent Build / Benchmark / WPT
            ↓
Canary / Telemetry
            ↓
Learn
核心判断：Browser Self-Improvement 的 Observe 层不能直接把 Agent 判断当事实。Crash、Regression、性能异常、兼容性问题都应该先经过可重复的 Validation Contract，确认“这是一个真实且稳定可重现的问题”，再消耗昂贵模型做 Diagnosis 与 Patch。

把“问题发现置信度”和“修复置信度”分开

一个完整工程资产最好同时记录两组证据：

Issue Evidence
├─ reproduction rate
├─ affected platform / version
├─ trace / crash signature
└─ independent validation result

Patch Evidence
├─ build / unit / WPT
├─ benchmark delta
├─ cross-platform regression
└─ canary / telemetry result

这样 Learn 阶段就不会把“误报但碰巧改了点东西”和“真实问题被可靠修复”混在一起。

今天的一个判断

Browser Self-Improvement 的第一道 Gate 应该前移到“问题是否真实”

以前容易把闭环画成 Telemetry → Agent Diagnose → Patch。Chrome Security 的实践提醒我们，更稳妥的路线是：

Observe
  ↓
Candidate Problem
  ↓
Validate the Problem
  ↓
Diagnose
  ↓
Patch
  ↓
Validate the Patch
  ↓
Canary
  ↓
Learn

也就是对问题和修复做两次独立验证。对于 Chromium / V8 / Skia / Network / WebGPU 这种复杂系统，这会比单纯增加 Agent autonomy 更能提升长期闭环质量。
