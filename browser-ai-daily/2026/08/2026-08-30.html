浏览器 × 端侧 AI 日报

今天高质量的浏览器引擎官方更新不多，但 Browser Agent 与 Self-Improvement 两条线出现了很清晰的工程信号：本地真实浏览器正在接入 MCP / WebMCP；同时 Harness 开始从“固定配置”变成可按任务即时生成、按轨迹选择性学习的系统。

2026-08-30 · 过去 24 小时优先 + 一周内未推送高价值补充

今天最值得看

FirefoxLocal MCP

Browser for AI Agent：Firefox 侧也出现“真实浏览器 + Native Messaging + MCP + WebMCP”组合

Firefox Add-ons 上的 Browser for AI Agent 在 8 月 29 日更新到 0.2.5。它通过本地 Native Messaging Host 暴露 MCP 服务，让 Agent 读取当前 Tab、URL、页面错误、localStorage、Cookie，并调用页面工具；同时支持页面通过 WebMCP 暴露工具。

启发：过去几天 Chrome / Firefox 上都在出现同一种 Local Browser Bridge：Extension 负责浏览器能力，本地进程负责 Agent 协议。真正需要标准化的将是权限、身份、审计和 Tool 生命周期，而不只是 click / type API。

Firefox Add-ons

HarnessJIT

JIT-Agent：Harness 不再只是长期优化一个固定版本，而是针对每个任务即时生成

JIT-Agent 将 Harness 拆成 memory、planning、action、capability orchestration 四个可执行模块。给定任务后，它现场生成任务特定 Harness；执行失败可以做 bounded repair，积累反馈后还能更新 Harness archive。论文报告其生成的 Harness 能跨多个模型家族带来增益。

对浏览器工程的意义：不同 Regression 不一定该共享一套固定 Agent Workflow。Crash、网络性能、Compositor、WebGPU 回归完全可以有不同的 Trace 采集、工具暴露、并发策略与验证路径，Harness 应按问题类型即时组装。

arXiv: 2608.25593

LearningTrajectory Quality

SWE-Prime：任务“成功”不等于这条轨迹值得学习

SWE-Prime 先按过程质量、结果质量和代表性筛选成功轨迹，再把轨迹拆成语义段，只让真正有贡献、可学习且风险可控的段参与训练。论文称仅使用筛选出的 10% 成功轨迹，反而优于完整 resolved dataset。

这直接影响 Browser Self-Improvement：一次 Regression 修好了，不代表其中所有搜索、猜测、无效命令和偶然步骤都应该沉淀成 Skill。Learn 层需要做 trajectory / segment selection。

arXiv: 2608.27449

浏览器技术

Local Browser Bridge 正在跨 Chrome / Firefox 收敛

Browser for AI Agent 这次更新最值得关注的不是功能列表，而是其分层方式：浏览器扩展保留真实 Session、Cookie、Tab 和页面状态；本地 Native Host 将这些能力转成 MCP；网页还能通过 WebMCP 提供更高层 Tool。

AI Agent
   │
Local MCP Server
   │
Native Messaging
   │
Browser Extension
   │
Real Firefox / Chrome Session
   ├─ Tab / DOM / Storage
   ├─ Page Errors
   └─ WebMCP Tools
产品判断：未来 Browser Agent Runtime 很可能同时需要两类 Tool：Browser-native Tool 与 Page-provided Tool。前者由浏览器掌控权限，后者由网站定义业务语义。

但现有扩展的权限仍然太宽

该 Firefox 扩展申请了所有网站数据、Cookie、History、Downloads、Tab、Native Messaging 等广泛权限。对于实验性本地 Agent 很方便，但如果成为日常 Browser Runtime，这种授权模型不够细。

应继续坚持：Capability 必须能绑定 Tab / Origin / Operation / Data Class，并且 WebMCP Tool 也不能绕过浏览器级授权。

端侧 AI

今天没有值得单独推送的新端侧模型或 WebGPU Runtime 发布

过去 24 小时内没有发现足够高质量、且与浏览器端侧推理直接相关的新官方发布。相比补普通模型新闻，今天更值得关注 Harness 与 Local Browser Bridge，因为它们决定端侧模型真正进入浏览器后“如何被调用、如何被验证、如何被限制”。

浏览器 × AI

JIT Harness 可以成为 Browser AI Router 之上的下一层

此前我们把 Browser Agent Runtime 拆成 capability tier、live pressure、privacy policy 和 AI Router。JIT-Agent 提醒我们：模型路由之后，还需要决定“这次任务应该以什么执行协议运行”。

Browser Task
    ↓
Task Classifier
    ↓
AI Router
(Local / Cloud / Model Size)
    ↓
JIT Harness Generator
    ├─ Memory policy
    ├─ Planning strategy
    ├─ Action protocol
    └─ Capability set
    ↓
Browser Runtime / WebMCP / DevTools
例子：网页填表任务需要短 Memory + 强权限确认；性能 Regression 需要 Trace + Pinpoint + benchmark；Crash RCA 需要符号、日志和 bisect。没必要都塞进一个“大而全”的 Harness。

Browser Self-Improvement

今天的新关键词：Selective Learning（选择性学习）

过去一周我们逐步补了 Memory Hygiene、Executable Learning、Reviewable Improvement、Trusted Learning 和 Privilege-Preserving Learning。SWE-Prime 补上了另一个缺口：即使结果成功，也不能默认整条轨迹都是正样本。

Telemetry / Regression
        ↓
Diagnose + Execute
        ↓
Successful / Failed Trajectory
        ↓
Trajectory Quality Filter
        ↓
Segment Contribution Filter
        ↓
Case Gate + Regression Gate + Security Gate
        ↓
Trusted Skill / Rule / Training Data
迁移到 Chromium：可以把 Agent 的一次性能修复轨迹切成“有效诊断步骤 / 无效探索 / 偶然成功 / 风险命令 / 最终验证”几个段，只把可重复、因果更明确的部分进入长期 Skill 或后续训练集。

JIT-Agent 让 Improve 层从“改 Skill”进一步变成“生成本次 Harness”

之前的路线主要是让 Agent 根据历史经验修改 Skill / Rule / Workflow。JIT-Agent 更进一步：保持一个固定协议边界，但允许针对具体问题实例组装不同的 memory、planning、action 与 capability 模块。

更适合浏览器工程的做法：Self-Improvement 不一定产出一个越来越大的全局 Agent；也可以产出一个 Harness Factory，让下一次问题现场构造最小、最相关、权限最小的执行环境。

今天的一个判断

Browser Self-Improvement 不应该演化成“一个越来越复杂、越来越难控制的超级 Harness”。更合理的方向是：

Fixed Safety / Capability Protocol
            +
   Harness Factory / Archive
            ↓
按问题即时生成最小 Harness
            ↓
执行并收集轨迹
            ↓
只选择真正有贡献的轨迹片段学习

因此，今天把长期原则再补一条：Selective Learning。成功只能证明结果，不证明过程值得继承。
